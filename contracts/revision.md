## Этап 2: trackerauth + torrents (решения от 2026-06-11)

### Р-1. Границы: скачивание .torrent уходит из qBit-клиента
**Было:** `qbittorrent.py:add_torrent()` сам скачивал .torrent с
трекеров, зная их причуды (Referer Кинозала, заголовки RuTracker).
**Решено:** `torrents` говорит только с qBittorrent API; скачивание
.torrent и кэш `torrent_cache/` — у `sources`; авторизованные
запросы к трекерам — query `trackerauth.fetch`. Трекеро-специфика
живёт у владельцев трекеров. *(Согласовано пользователем.)*

### Р-2. Hash торрента вычисляется локально
**Было:** временный тег + поллинг qBit до 15×2 с, теговые баги,
неразличимый «Fails.».
**Решено:** infohash v1 считается из .torrent-файла (SHA1 байтов
секции `info`), для magnet берётся из `btih` (hex и base32);
`btmh`/чистый v2 — явная ошибка «не поддерживается», не молчание.
Страховки: юнит-тест на реальных файлах (hash обязан совпасть с
qBittorrent), контрольный запрос по hash после добавления.
*(Согласовано: «всё звучит отлично».)*

### Р-3. Сессия qBittorrent эфемерна, SID в БД не хранится
**Было:** SID сохранялся в `settings`; при старте почти всегда
протухший → 403-шум (находка №8), дубль чужого состояния в БД.
**Решено:** логин при старте (~100 мс, локальный сервис без лимитов);
на 403 посреди работы — тихий релогин и повтор сорванной операции,
ошибка наверх только при повторной неудаче. *(Согласовано.)*

### Р-4. Сессии трекеров — наоборот, персистентны
**Было:** куки трекеров жили только в памяти → каждый рестарт = новые
логины (при хронических рестартах прода — сотни логинов на Кинозал);
живость сессии никогда не проверялась — протухание ломало парсинг
далеко от причины.
**Решено:** куки хранятся в БД (таблица `tracker_sessions`, владелец
trackerauth; добавляется Alembic-миграцией поверх базовой схемы);
при первом использовании после рестарта — дешёвая проверка живости;
детект протухания посреди работы → релогин → повтор запроса (один
раз); логины с ограничением частоты на трекер.
**Мотив пользователя (ценность проекта):** частые логины и лишние
запросы вредят чужому сайту — «мы хотим уважать других». Это правило
распространяется на все внешние обращения системы (парсеры, сканер).
*(Согласовано.)*

### Р-5. HTTP-стек
**Решено:** httpx (async) — для qBittorrent API; requests +
cloudscraper в executor с жёсткими таймаутами — для трекеров
(cloudscraper необходим для Astar за Cloudflare и работает только
поверх requests). Любой сетевой вызов обязан иметь таймаут —
зависание одного модуля не должно замораживать процесс (находка №7).
*(Согласовано после разъяснения sync/async/executor.)*

### Р-6. Девять мёртвых таблиц не входят в базовую схему
**Контекст:** находка №1 — в прод-БД 29 таблиц, в коде используются 20.
**Решено:** Alembic-миграция №1 (базовая схема новой системы) включает
только живые таблицы; при финальном переключении лишние таблицы в
копии прод-БД не мешают и чистятся отдельной миграцией после
стабилизации.

### Вне ревизии (констатации)
- Стадия `awaiting_metadata` для magnet — физика протокола (анкета
  доезжает от пиров позже hash), сохраняется в новом `torrents`.
- Детект HTML-ответов при скачивании .torrent («суточный лимит»,
  «включите JavaScript») — требование к `sources` (этап 3).
- Long-poll `sync/maindata`: таймаут — норма, не ретраить.
- 404 от qBit = ресурса нет, не ретраить.

### Р-7. БД — приватное хранилище модуля, не участник шины
**Вопрос пользователя:** «модуль базы данных — такой же модуль на
шине?» **Решено (после разбора):** нет. БД — приватная память модуля
(состояние между перезапусками), межмодульное общение — только шина.
Дисциплина, делающая это безопасным:
- каждая таблица принадлежит ровно одному модулю (карта — ТЗ, раздел 6);
  чужие данные — только query через шину; канал к чужим данным мимо
  шины запрещён;
- SQL инкапсулирован в `repository.py` модуля, не размазан по коду;
- значимые изменения данных модуль публикует событием в шину —
  «что меняется» видно на шине, «как лежит» — приватно;
- обращения к БД логируются группой модуля (принцип 6).
**Отвергнутая альтернатива** (БД-модуль на шине): возвращает god-object
уровня старого db.py, ломает транзакции (конверт не переносит открытую
транзакцию), на порядки дороже на каждый доступ к собственным данным.
*(Согласовано пользователем.)*

## Этап 3: движок правил (решения от 2026-06-11)

### Р-8. Семантика нового движка правил
Формат блочных правил в БД — констрейнт (профили пользователя работают
как есть). Семантика повторяет фактическую, кроме трёх согласованных
исправлений:
- **(А, баг — чинить)** несколько извлекающих действий в одном правиле:
  у каждого действия свой regex и СВОЯ нумерация capture-групп; старый
  сквозной счётчик молча терял все извлечения после первого успешного
  (подтверждено на 5 правилах в 3 профилях; у «AniDub VK Rules»
  терялся сезон).
- **(Б)** битое/пустое условие — громкая ошибка валидации профиля:
  правило помечается неисправным и не применяется, в лог — что именно
  сломано; старое поведение (условие тихо исчезает, правило ширеет) —
  запрещено.
- **(В)** остановка обхода (continue_after_match=0) — только если
  правило ДАЛО результат (извлекло данные или exclude); «условия
  совпали, но шаблон извлечения нет» больше не глушит каскад. На
  текущих профилях пользователя поведение не меняется (в их
  стоп-правилах условие = шаблону извлечения); пользователь: «то, что
  было, — скорее всего борьба с чем-то другим, поэтому так нелогично».
Сохраняется как есть: OR-группировка условий (оператор связывает со
следующим, группы И через ИЛИ), правило «отрицательный результат
add/subtract игнорируется» (именное правило пользователя),
регистронезависимость, перезапись полей поздними правилами, ключи
extracted (episode/season/start/end/voiceover/quality/resolution).
Новое: компиляция профиля один раз с кэшем (вместо рекомпиляции на
каждое название).
**Верификация:** дифф старого и нового движков на ~1100 реальных
названиях из фикстуры (350 VK + 737 файлов торрентов), каждое
расхождение разбирается поимённо. *(Согласовано.)*

### Р-9. Модуль sources: факты вместо решений, API вместо браузера
- Контракт `sources.parse` → {title, releases[]}: парсер отдаёт ФАКТЫ
  (ссылка/магнет, маркер даты, серии, качество); решение «ново/старо»
  принимает scan. Старый протокол link=None упразднён.
- Anilibria — через официальный публичный API (находка 12), включая
  готовый infohash. *(Пользователь: «API — лучшее, что можно
  придумать, однозначное согласие».)*
- Маркеры дат — в исторических форматах трекеров (находка 13, защита
  от массовой перекачки при переключении).
- Доставка страниц: kinozal/rutracker — через trackerauth.fetch;
  astar/anilibria_tv — общий Playwright-пул на этапе 6 (находка 14:
  сейчас ими никто не пользуется; функции разбора готовы и
  протестированы по коду).
- Межзапросная пауза на трекер (3 с) + замок «одна операция на трекер»
  («уважать других»).
- Скачивание .torrent (Р-1) — здесь же: кэш torrent_cache/, детект
  HTML-ответов (суточный лимит, JS).

### Р-10. Планировщик покрытия и VK-источник
- Семантика SmartCollector v4.1 перенесена 1:1 как чистая функция
  modules/scan/planner.py, КРОМЕ согласованного **фикса Г (находка
  22)**: лучшая одиночка выбиралась инвертированно (max вместо min
  ключа качества — худшее разрешение / последний в списке приоритетов
  пользователя; этап апгрейда в том же алгоритме считал наоборот).
  Пользователь: «чинить, приоритет за наивысшим качеством единичной
  серии». Дифф со старым кодом: 9/10 реальных сериалов идентичны,
  1 согласованное отклонение (сериал 87: выбран 2160p вместо 1080p).
- VK — источник в sources через официальный VK API (находка 15):
  токен не покидает trackerauth (провайдер vk подмешивает его в
  параметры), таймауты на всех вызовах (находка 17 — кандидат в
  первопричину зависаний прода), пауза между страницами пагинации,
  предохранитель на 50 страниц.
- **Формулы идентификаторов — констрейнт данных** (существующие записи
  обязаны совпадать): unique_id медиа-элемента =
  md5(url + pub_date.strftime('%Y-%m-%d %H:%M:%S') + series_id)[:16];
  torrent_id = md5(link + date_time)[:16]. Применяются в scan (этап 4).
- Статусы плана: 'replaced' = эпизоды накрыты планом, 'redundant' =
  не накрыты (семантика оригинала сохранена).
- Оркестратор сканирования (цепочка сканов, зеркала-фоллбэк,
  scan_tasks-ресьюмабельность, fixed/rolling замены) — этап 4, вместе
  с конвейером, который он запускает.

## Этап 4: конвейер (решения от 2026-06-12)

### Р-11. Статусная модель: вычисляемая, на свёртках, без хранения
Разбор показал три этажа хранения одного факта (задачи → флаги
series_statuses → строка series.state), поллинг-пересчёт каждые 5 с по
всем сериалам с безусловным broadcast (механика SSE-шторма, находки 4 и
25) и эфемерный по природе viewing в персистентной БД с heartbeat-
таймером на фронте. Согласовано с пользователем:

- **Статус сериала нигде не хранится** — это вычисляемое значение
  (принцип 7). Новая система не пишет и не читает ни series.state, ни
  series_statuses; физически таблица и колонка остаются в схеме
  (инвариант Alembic 0001) до зачистки отдельной миграцией после
  переключения. Пересчёт при старте процесса — приемлем
  («пусть пересчитываются, главное — правильно»).
- **Свёртки вместо опроса**: модуль-владелец задач публикует событие
  `series.status.contribution {source, series_id, flags}` в момент,
  когда его вклад изменился (он сам только что записал это в свою
  таблицу), и при старте после reconcile. Допустимые флаги: scanning,
  metadata, renaming, checking, activating, downloading, slicing,
  ready, error, waiting. Все false = вклад снят.
- **Агрегатор в catalog** (владелец таблицы series): держит вклады в
  памяти (эфемерный кэш, восстанавливается публикациями поставщиков
  при старте), складывает в набор, сортирует по единой иерархии
  (error … waiting — как старый STATUS_HIERARCHY, источник порядка
  пилюль) и публикует `series.status.changed {series_id, statuses}`
  **только при изменении набора**. Пустой набор = ['waiting'].
- **Разная семантика waiting сохранена как осмысленная**: у VK waiting
  приходит в свёртке владельца media_items («есть pending в плане,
  нет активности») и сосуществует с ready (фронт: stripes-stopped);
  у торрентов waiting — только «нет никаких вкладов».
- **viewing — эфемерное состояние в памяти catalog**: команды
  catalog.viewing.start/stop (открытие/закрытие модалки — действия
  пользователя), страховка — событие gateway.sse.clients {count}:
  при count=0 все viewing сбрасываются. Исчезают: DateTime в БД,
  setInterval-heartbeat 30 с на фронте (правка JS — на этапе 5 по
  согласованию), стейл-чекер каждые 5 с. Осознанный компромисс: при
  двух вкладках смерть вкладки с модалкой не сбросит viewing, пока
  жива вторая; усиление (client_id) — на этапе 5, если потребуется.
- **Ошибка получает носителя** (согласовано): задача конвейера при
  ошибке не удаляется, а переходит в stage/status='error' с сообщением;
  ошибка скана — scan_tasks.status='error'. error сериала = «есть
  незакрытая задача-ошибка», сброс — повторным сканом или действием
  пользователя. Это же — честная замена /api/agent/reset (находка 23).
- Контракт с фронтом: массив statuses в payload оживляет мёртвую ветку
  `s.statuses || s.state.split(...)` (находка 24) — JS пилюль/слоёв
  не меняется, визуал идентичен.

### Р-12. Оркестратор сканирования (согласован 2026-06-12)
Разбор: находки 26 (фиктивная ресьюмабельность scan_tasks — recovery
никем не вызывался, незавершённые задачи удалялись), 27 (скан без
блокировок: ручной в HTTP-запросе + автоскан могли пересечься),
28 (тип замены — подстрока 'astar' в оркестраторе), 29 (мусор).
Решения:

- **Зеркала-фоллбэк переехали в sources** (владелец таблицы trackers и
  доставки): sources.parse сам перебирает зеркала, scan о них не знает;
  результат несёт фактический URL.
- **Сравнение «обновилось ли» — по torrent_id** (md5(link+date_time),
  формула-констрейнт Р-10, верифицирована на фикстуре 190/190; для
  anilibria link = magnet — так в прод-данных). Протокол link=None
  старых парсеров не воспроизводится (Р-9).
- **Настоящая ресьюмабельность**: план замен — в scan_tasks ДО
  выполнения; шаги идемпотентны (локальный infohash, повторное
  добавление = existed); on_start возобновляет незавершённые задачи.
  Ошибка — scan_tasks.status='error' (+текст в results_data['error'],
  отдельной колонки в фиксированной схеме нет) — носитель свёртки
  error (Р-11); сбрасывается следующим сканом.
- **Параллельный скан сериала отклоняется** (`not_allowed` по таблице допустимого,
  409 по коду); защита и от гонки ручного с автосканом.
- **Переобработка имён перед сканом** — query renaming.reprocess
  (закрывает находку 16: сон до 600 с заменён request/reply); пока
  модуль renaming не подключён — громкий warning и пропуск.
- **fixed/rolling сохранены семантически** (fixed: замена по совпадению
  episodes — astar; rolling: замена единственного активного, при 2+
  активных не заменяем), но в явной таблице REPLACE_MODE.
- **VK-ветка**: апсерт media_items с «фантомной» защитой (1:1 со
  старым: удаляются только девственные), план — только из
  plan_status='candidate' (семантика SmartCollector), запись
  publication_date в формате хранения прод-БД; завершение —
  событие scan.plan.updated: создание download_tasks и усыновление
  файлов — зона владельца download_tasks (downloads, следующий разбор).
- **Расписание автоскана** — в самом scan: тики читают settings
  (scanner_agent_enabled, next_scan_timestamp); после полного прохода
  следующий скан назначается по опустошению конвейера — событие
  torrents.queue.changed {count} вместо опроса; состояние публикуется
  событием scan.status.changed (контракт scanner_status_update).
- **core: handle(..., concurrent=True)** — конверты топика
  обрабатываются отдельными задачами; иначе долгий скан блокировал бы
  очередь запросов модуля (урок теста на гонку; родственно находке 7).
  По умолчанию по-прежнему последовательно (порядок свёрток важен).
- Контракты будущих модулей зафиксированы фейками тестов:
  renaming.reprocess, torrents.db.active / db.deactivate_all /
  register (идемпотентен) / queue.get / queue.changed.

### Р-13. Модуль downloads (согласован 2026-06-12)
Разбор: находки 30 (полный список очереди в SSE каждые 5 с), 31 (error
ретраится только рестартом сервиса, скан плодит дубли задач), 32
(pending вне плана зависают навсегда). Решения:

- **Жизнь по событиям**: обработчик scan.plan.updated (усыновление →
  создание задач → чистка pending вне плана → пинок диспетчеру);
  диспетчер добирает задачи при создании/завершении/смене лимита —
  тик 5 с не воспроизводится. Лимит параллелизма — подписка на
  settings.changed.
- **yt-dlp асинхронным subprocess'ом** (zависание процесса не держит
  модуль), прогресс: запись в БД с троттлингом 2 с (как было) +
  событие downloads.queue.changed при изменениях (троттлинг 1 с) —
  контракт SSE download_queue_update сохранён, шторм устранён.
- **Политика ретраев**: ошибка — носитель (задача status='error' +
  элемент error, свёртка Р-11); ретрай — следующим сканом: error-задача
  заменяется новой, error-элемент снова подхватывается (старая система
  подхватывала его ТОЛЬКО рестартом). При старте reconcile возвращает
  в очередь лишь оборванные 'downloading'; error рестартом не лечится.
- **Фоновая ФС-проверка раз в 60 с не воспроизводится** (решение
  пользователя): синхронизация с диском — при каждом скане и query
  downloads.fs.sync {series_id} (пропажи → pending, находки →
  completed); gateway на этапе 5 вызывает fs.sync при открытии модалки
  статуса (там показывается актуальный список файлов).
- **Свёртка**: downloading/error по элементам плана, ready по всем
  неигнорируемым, waiting=«есть pending в плане» — семантика
  sync_vk_statuses. В агрегатор добавлено правило «waiting подавляется
  активностью (кроме ready/viewing)» — в старом коде это поведение
  было размазано по двум конфликтующим механизмам (_sync_waiting_status
  vs sync_vk_statuses), теперь детерминировано.

### Р-14. Торрент-конвейер (согласован 2026-06-12)
Разбор стадийной машины Agent + мониторинга MonitoringAgent.

- **ИНВАРИАНТ ЯДРА (зафиксирован пользователем)**: торрент стоит на
  паузе с момента добавления и до завершения переименования файлов.
  Единственное исключение — magnet: списка файлов нет без метаданных,
  торрент запускается РОВНО на время их получения и немедленно
  ставится обратно на паузу. Любая закачка до переименования кладёт
  файлы под исходными именами и ломает зачёт существующих при
  replace-recheck (докачка только нового — сердце экономии трафика).
  В машине это закреплено: стадия awaiting_pause при любом активном
  состоянии отвечает force_pause; тесты проверяют порядок
  pause → rename → recheck → resume.
- **Стадии** — значения в БД старые (констрейнт данных + карта
  стадия→флаг Р-11), машина — чистая решающая функция
  (modules/torrents/pipeline.py). Отличие одно: переименование
  выполняется на стадии 'renaming' (раньше пустышка, работа делалась в
  конце 'awaiting_pause_before_rename') — поведение идентично.
  В семейства состояний добавлены stopped*-имена qBit 5.x.
- **Ошибка — носитель**: stage='error', задача не удаляется (текст — в
  лог: в схеме agent_tasks нет колонки), свёртка error; ретрай —
  повторной регистрацией (следующий скан). Автоскан пропускает сериал
  с активными задачами конвейера (как старый); ручной скан — нет.
- **Переименование** — query renaming.process_torrent {series_id,
  qb_hash} (зона renaming; контракт зафиксирован фейком тестов).
- **Мониторинг прогресса** — адаптивный опрос qBit (5 с при
  активности, 60 с в покое), запись в download_tasks (torrent),
  свёртка downloading/ready по семантике sync_torrent_statuses
  (+stopped*), публикация только при изменении (кэш флагов).
- **torrents.fs.verify {series_id}** — проверка файлов на диске +
  missing → recheck-задачи; вызывается сканом и при открытии модалки
  (распространение Р-13 на торренты, согласовано). Вернувшийся файл
  missing → renamed.
- Реализованы контракты Р-12: db.active (сверка с qBit),
  db.deactivate_all, register (идемпотентен: upsert по torrent_id,
  замена старого — деактивация + удаление из qBit без файлов +
  чистка torrent_files), queue.get {series_id?},
  событие queue.changed {count, tasks} (count=0 — сигнал scan).

### Р-26. Блок «Диапазон» в конструкторе правил парсера (2026-10-19)
Разбор: массовая фильтрация и отсечение серий и компиляций (например, исключить
серии 1–180 в тайтле на 212 серий) через визуальный конструктор шаблонов.
Решения:

- **Новый тип блока `range` («Диапазон»)**:
  - Доступен в конструкторе условий «ЕСЛИ» (в действиях «ТО» недопустим).
  - Спецификация (`parse_range_spec`): интервалы `1-180`, списки `1, 3-10`,
    нормализация инверсий (`10-1` → `1-10`), объединение смежных отрезков.
- **Семантика компиляций («Задета исключением»)**:
  - Компиляция `[comp_start, comp_end]` и фильтр правила `[r_start, r_end]`:
    пересечение считается по формуле $\max(\text{comp\_start}, r\_start) \le \min(\text{comp\_end}, r\_end)$.
  - Если компиляция содержит хотя бы одну серию из исключаемого диапазона
    (например, `170-190` при правиле `1-180`), она исключается целиком.
- **Симметричная защита от маркеров разрешений**:
  - Суффиксы качества (`p`, `i`, `k`, `р`, `к`, `1080p`, `1080i`, `4к`)
    проверяются в обоих направлениях (lookahead, lookbehind и явный двухчисловой
    шаблон), исключая ложные срабатывания вида `170-1080p`.
- **Защита от дурака и Решение Б**:
  - Блок диапазона обязан следовать сразу за числом; запрещены числа после диапазона;
    запрещён диапазон в действиях «ТО».
  - Нарушение правил валидации громко переводит правило в `invalid_rules`
    по контракту Р-8 (Решение Б) без падения сервиса.
  - Во фронтенде: палитра предотвращает дублирование диапазонов, а при сбросе в
    пустое условие автоматически подставляется блок `Число`.


### Р-27. Каскад удаления серии: номера, прерывание скана, отчёты о чистке (2026-10-20)

Разбор: удаление серии оставляло за собой скрытые риски — номер серии
переиспользовался, идущий скан продолжал работу после удаления, часть
серийных таблиц не проверяла существование серии, а обрыв каскада не был
виден никому.

Решения:

- **Номера серий не переиспользуются**: `series.id` переведён на
  `INTEGER PRIMARY KEY AUTOINCREMENT` (миграция 0011). Удалённый
  максимальный номер больше не занимается новой серией — новая серия
  не наследует media_unique_id удалённой (в хэш входит series_id).
- **Id новой серии берётся у базы**: `catalog.create_series` возвращает
  `lastrowid` вставленной строки вместо чтения максимального id — при
  параллельном создании серий вызовы больше не получают id чужой серии.
- **Идущий скан прерывается (Д2)**: scan, как загрузка, нарезка и перенос
  файлов, прекращает работу удалённой серии; носитель ошибки в scan_tasks
  не пишется для несуществующей серии.
- **Внешние ключи на series во всех серийных таблицах** (миграция 0012):
  download_tasks, scan_tasks, slicing_tasks, renaming_tasks,
  relocation_tasks. Опоздавшая запись отбивается, а не оседает сиротой.
  Удаление серии остаётся с `enforce_fk=False` (Р-19): родителя удаляет
  catalog, детей дочищают владельцы по событию.
- **Отчёты о чистке**: каждый владелец серийных таблиц публикует
  `series.purged {series_id, owner}`; catalog ждёт отчёты и пишет в лог,
  кто не отчитался — обрыв каскада больше не остаётся незамеченным.

### Р-28. Приоритет правил над карточкой сериала (2026-10-20)

Разбор: имя файла собиралось по обратной иерархии — ручной ввод в карточке
сериала («Качество (ручной ввод)», «Разрешение (ручной ввод)») перебивал и
правило, и факт из БД. Одна карточка — одна причина на все файлы серии,
поэтому файл 1080p в серии с ручным «2160p» получал имя 2160p, а правило,
сработавшее именно на этом файле, не влияло ни на что.

Решения:

- **Иерархия «правило > значение карточки > факт БД»** для качества,
  разрешения и номера сезона. Сработавшее на конкретном файле правило
  побеждает; значение карточки работает дефолтом, когда правило ничего не
  дало. Сезон резолвится по тому же принципу (`core/season.py`) — иерархия
  одна на все поля.
- **Оверрайд карточки перестал быть абсолютным**: он и раньше перебивал факт
  из БД, но больше не перебивает правило. То, чего правила не знают (например
  «HDR10+» в «HDR10+ WEB-DL»), в имя файла не попадает — это выражается
  правилом, а не ручным вводом.
- **Значения карточки подставляются в одном месте** (`formatter.merge_series_defaults`),
  а `format_name` читает только сводные метаданные: приоритет не дублируется
  по двум функциям.
- **Словарь конструктора — один перечень в движке** (`ACTION_TYPES`,
  `CONDITION_TYPES`, `EXTRACT_TYPES`, `ASSIGN_TYPES`, `BLOCK_TYPES`), плюс
  сверка с панелью тестом: значение, которого не знает движок, ломает
  сохранение правила (API отвечает 400).
- **Неизвестные значения отвергаются при записи** — тем же компилятором,
  что и применение профиля, без второго валидатора. Правило, сломанное до
  появления проверки, отключается с причиной в логе, а не роняет профиль.
- **Список правил отдаёт `valid` и `error`**: неисправное правило видно в
  панели, а не только в логе на сервере.
- **Обновление правила не стирает условия, если поле не прислано**: раньше
  для `name` и `action_pattern` «не прислал» означало «не трогай», а для
  `conditions` — «удали всё», и правило «ЕСЛИ сезон ТО назначить сезон»
  превращалось в безусловное. Удалить условия можно, прислав `[]`.

### Р-29. Блоки-приложения: «Диапазон» и «±» пристёгнуты к числу (2026-10-20)

Разбор: «Диапазон» ввели с ограничениями — он должен стоять после числа, а
блоки «+»/«−» остались без ограничений вовсе. Модификатор срабатывал только
если блок стоял сразу за числом, а в остальных случаях молча игнорировался:
правило «+5» перед числом или после текста выглядело работающим, но сдвига не
давало. В условии «ЕСЛИ» блок «±» вообще не участвовал в регулярном выражении
и ошибки не вызывал — API принимал такое тело, а панель такие блоки в «ЕСЛИ»
и не предлагала. Панель к тому же показывала «Диапазон» отдельным блоком рядом
с числом, хотя по смыслу это его хвост.

Решения:

- **Блок-приложение — хвост числа**: `range`, `add`, `subtract` меняют или
  фильтруют число, за которым стоят, и потому пристёгнуты к нему. Правила
  одинаковы для всех трёх видов: блок один на шаблон и стоит сразу за
  **последним** числом. Отдельный «последний» снимает неоднозначность, к
  какому числу относится блок, — как это уже сделано для «Диапазона».
- **Ограничение переехало в движок**: «±» вне своего места и «±» в условии
  «ЕСЛИ» — ошибка правила (API отвечает 400), а не тишина. Проверка живёт в
  том же компиляторе, что и применение профиля, поэтому проверка и исполнение
  не расходятся.
- **Панель пристёгивает блок сама**: снятый с палитры или перетащенный мимо
  числа блок прыгает за последнее число; числа в шаблоне нет — создаётся.
  Правильно стоящий блок не трогается: ручная расстановка пользователя
  сохраняется.
- **Вид**: блок-приложение рисуется единым телом с числом — без зазора, с
  прямыми соприкасающимися углами. Формат хранения блоков не менялся: ни
  миграции правил, ни правки формата хранения блоков.
- **Логика привязки вынесена из компонента** в `web/src/lib/patternBlocks.ts`:
  она покрыта тестами, а правило одно и то же в панели и в движке.

### Р-30. Защиты конструктора: блок-приложение несовместим со вторым числом (2026-10-20)

> **Позже заменено Р-31**: на момент принятия этого решения ограничения API и
> панели ещё расходились. Формулировки ниже — в состоянии на дату решения.

Разбор: панель не сообщала о недопустимом блоке — защита стояла только для
«Диапазона», а второй «±» вставлялся в шаблон, и ошибка вылезала лишь при
сохранении. Второе следствие того же правила: блок-приложение принадлежит
числу, а при двух числах принадлежность становится спорной, и запрет «± после
числа, но не последнего» выглядел как искусственное ограничение.

Решения:

- **Шаблон — либо несколько чисел, либо одно число с блоком-приложением.**
  В шаблоне с блоком-приложением число добавить нельзя; в шаблоне с двумя
  числами блок-приложение добавить нельзя.
- **Запрет виден в палитре, а не молчит**: недопустимый блок серый и с
  причиной в подсказке, перетащить его нельзя.
- **Проверяется шаблон-получатель.** Сортировка отдаёт проверку списку, из
  которого блок тянут, поэтому список назначения берётся из цели переноса
  (`relatedContext.list`), а не из редактора, где начался перенос. Раньше
  проверка смотрела на свой шаблон — из-за этого перенос блока между
  условиями и действиями блокировался не по делу.
- **Блок-приложение нельзя перенести в чужой контекст**: `range` — в
  действие «ТО», `add`/`subtract` — в условие «ЕСЛИ» не переносятся. Это
  правило движка, и раньше панель могла составить правило, которое
  сохранить нельзя.
- **Движок на момент решения не менялся**: он требовал, чтобы блок-приложение
  стоял сразу за последним числом, и состояние «два числа и блок-приложение»
  через API создать было можно — панель его просто не предлагала собрать.
  Это расхождение закрыто Р-31.

### Р-31. API и панель ограничены одинаково (2026-10-20)

Разбор: после Р-30 панель и движок расходились — панель не давала составить
шаблон «два числа и блок-приложение», а API такой шаблон принимал. Любой
клиент API мог собрать правило, которое панель показать не может.

Решения:

- **В шаблоне с блоком-приложением — ровно одно число.** Движок требует того
  же, что и панель: блок-приложение стоит сразу за единственным числом
  шаблона. Нарушение — 400 с причиной.
- **Ушёл явный шаблон компиляции из двух чисел с «Диапазоном»** (например
  «число, -, число, диапазон»): при двух числах блок указывал сразу на два
  числа и менял смысл — «Диапазон» фильтровал не число, а пересечение
  диапазона-компиляции. Смысл сохраняется формой с одним числом, где
  компиляция «10-30» определяется по самому названию — но только для
  разделителей, которые движок распознаёт как границу компиляции
  (`-`, `–`, `—`, `по`, `to`); произвольный текст между числами такой формой
  не покрывается. В живых правилах используется именно одночисловая форма.
- **Ушёл и `extract_range` с двумя числами и «±»**: раньше принималось
  (сдвигалась вторая граница диапазона серий), теперь такой шаблон
  недопустим, как и в панели.
- **Мёртвый код удалён**: ветка «два числа» в проверке диапазона и поле
  `number_count` больше не нужны — блок-приложение всегда висит на единственном
  числе.
- **Живые данные не затронуты**: все 69 правил в 28 профилях собираются без
  ошибок, поведение на 3441 реальном названии не изменилось (96 348
  сравнений — ноль расхождений).

### Р-32. Замечания независимого ревью (2026-10-20)

Разбор: независимое ревью доработки (движок, панель, документация) нашло один
средний дефект и несколько мелких.

- **Удаление числа меняло смысл шаблона.** Если после блока-приложения шёл
  текст, пересозданное число вставало в конец, и шаблон становился другим по
  смыслу: движок исключал «10 серия», а переставленный — уже нет. Теперь
  число занимает место приложения, и форма шаблона сохраняется.
- **Пара «число + приложение» не делится.** Крестик у числа с приложением
  недоступен (с причиной в подсказке) — приложение сначала снимают; перенос
  такого числа в другой шаблон запрещён: внутри шаблона приложение следует
  за числом само.

### Р-33. Плееры 1.ruchime.org: адаптеры, Vibix и максимальное разрешение (2026-10-20)

без доступного VK уходила в очередь с мёртвой ссылкой.

- **Отчёт о доступности.** Скан сохраняет последнее состояние по серии

### Р-34. Сбой пробы не переключает источник и не понижает качество (2026-10-20)

### Р-35. Качество — только факт; исключённые серии не опрашиваются (2026-10-20)

### Р-37. Один файл на слот эпизода; поток проверяется до выбора (2026-10-28)

Разбор. Серии 53, 54, 80, 83, 84, 85: на диске лежали файлы разных разрешений
одного эпизода (11 лишних, ~1 ГБ). Имя файла содержит разрешение, поэтому
новое качество — новый файл. Планировщик помечал проигравшего `replaced`, но
файл не удалял никто. Вход планировщика — строки `plan_status='candidate'`, то
есть только вернувшиеся из последнего скана; веб-скан отдаёт один лучший факт
на эпизод, поэтому прежние строки выпадали из пересчёта и оставались
`in_plan_single` (серии 54, 80, 84, 85). Серия 80, эпизод 389: Vibix объявил
480p, манифест Kinescope отвечал 400 (не менялось 14+ часов), загрузчик отдавал
yt-dlp страницу серии, тот находил закрытый VK-ролик и выдавал его ошибку.

Решения.
- **План по всем строкам серии.** `scan` строит план по каждой известной строке
  и записывает его одной транзакцией (`Database.execute_many`); пропущенные
  планировщиком строки возвращаются в `candidate`, а не хранят устаревший
  статус.
- **`media_items.superseded_by` (миграция 0015).** Планировщик возвращает пару
  «проигравший одиночка → победитель его слота (сезон, эпизод, часть)».
  Накрытые компиляцией одиночки в пары не входят. Победитель определяется
  планом, поэтому пользовательский приоритет качества сохраняется.
- **Удаление проигравшего — в `downloads`.** `_retire_superseded` (после
  загрузки, усыновления, диспетчеризации, сверки диска) удаляет файл, только
  если победитель в плане, скачан и его файл есть на диске. Строка остаётся с
  `final_filename=NULL`: она помнит скачанное разрешение, скан не качает его
  заново, счётчик «скачано» не завышается. Общий файл и путь вне каталога серии
  не удаляются.
- **Устаревшая строка не держит слот.** План по всем строкам не включает строку,
  которую последний скан не предложил и которая не скачана (кроме качающейся):
  мёртвый кандидат со статусом `error` иначе выигрывал бы у рабочего источника
  ниже по разрешению (найдено живым сканом серии 80, эпизод 389). Error-задачи
  элементов вне плана чистятся вместе с pending. Предложенная сканом строка в
  `error` слот сохраняет и повторяется.
- **Лучший файл по скачанной ссылке — своя строка.** Если кандидат с большим
  разрешением приходит по ссылке уже скачанной строки (Vibix: ссылка — страница
  серии, одна на все качества), его `unique_id` считается
  `ids.upgrade_unique_id` (md5 с суффиксом `@<разрешение>p`); прежние id и
  формула Р-10 не меняются.
- **Vibix-кандидат проверяется по манифесту.** Проверяются только кандидаты,
  способные выиграть эпизод (разрешение выше уже найденного); при мёртвом
  манифесте берётся лучший читаемый поток ниже, иначе кандидата нет.
  Скачивание берёт лучший читаемый поток.
- **Страница серии — не поток.** Провайдер, узнавший свою ссылку без потока,
  бросает `StreamUnavailable`; `sources.video.stream` отвечает
  `{handled, error, transient}`, задача падает с этой причиной (временные
  причины повторяются). Для web-серии сбой самого запроса потока тоже ошибка
  задачи; для VK-серий остаётся путь yt-dlp.

За рамками: торрент-ветка (замена раздач — `_retire_replaced`, отдельная
система).

### Р-38. Источник dunhuatv.ru: плеер и озвучка выбираются пользователем (2026-10-28)

Источник веб-видео `dunhuatv.ru` (модуль `sources`, `video_providers/dunhuatv.py`).
Страница тайтла несёт два плеера: VK (агрегатор CDN VideoHub) и Kodik; у каждого —

- **Разбор ссылки** (`sources.parse` → `/api/parse_url`) отдаёт `sources` — список

  дырами, адрес с выбором), `selected_source` и список серий выбранного пункта.
  Две записи одной студии с разным типом (у VK это `Многоголосый` и
  `Неизвестный`) — два пункта, без склейки.

  «Получить с сайта» опрашивает именно эту озвучку.
- **Скан** опрашивает только серии выбранной озвучки; адрес кандидата — фрагмент
  страницы (`#vk=<vkId>` или `#kodik=<serial>/<hash>/<серия>`), идентификатор
  элемента стабилен, поток разрешается перед скачиванием (`sources.video.stream`).
- **Разрешение — факт.** Ступени лестницы VK до `FullHd` читаются по метке
  (144…1080), ступени выше (`4k`, `2k`, `Qhd`) измеряются `ffprobe`: метка `4k` у
  этого плеера оказалась кадром 2560×1440. Не измеренная ступень не выбирается.

- **Подпись CDN привязана к User-Agent** запроса, выдавшего ссылку: без него CDN
  отвечает 400. Провайдер отдаёт `User-Agent`, `Origin`, `Referer` в `headers`
  ответа `sources.video.stream`, загрузчик передаёт их в `ffprobe` и `ffmpeg`
  целиком (раньше доходил только `Referer`).
- **Временные сбои** (429, 5xx, обрыв) повторяются; если после повторов часть серий
  не прочитана, скан падает с просьбой повторить, а не отдаёт неполный план.

За рамками: объединение источников и хранение озвучек для выравнивания (миссия
`voice-alignment`, этапы 2 и 4).

### Р-40. Скачивание дополнительных озвучек (2026-10-28)

- **Общий исполнитель `downloads.fetch`**: поток ссылки скачивается в абсолютный путь вне
  `media_items` и `download_tasks`. Свой лимит параллелизма — настройка
  `max_parallel_dub_downloads` (по умолчанию 2). Три попытки на временные ошибки, недокачанный
  файл удаляется, итог — событие `downloads.fetch.finished`. Исполнитель не хранит состояние:
  владелец очереди пересылает команду после перезапуска. Разрешение потока ограничивает
  `max_height` (провайдеры: лучшая ступень не выше предела, иначе ближайшая выше).
- **Владелец очереди — `voices`**, таблица `voice_dubs` (миграция 0016): одна запись на
  (сериал, сезон, серия, озвучка) с цепочкой источников, номером попытки, статусом
  (`pending` / `downloading` / `ready` / `failed`) и временным путём. Ключ озвучки — наименьший
  токен имён группы: он не зависит от порядка списка сайта.
- **`voices.dispatch {series_id}`** шлёт скан после `downloads.dispatch` для `web_video`-серий:
  каталог сайта со ссылками → раскладка вокруг выбранного референса → записи по референс-сериям
  плана (`downloads.episodes.get`, соответствие серии плана серии сайта — обратный поиск ссылки
  референса) → загрузка недостающего. Временный каталог — настройка `voices.temp_root`
  (по умолчанию `/nas/torrents/series-tracker`), вне медиатеки.
- **Порядок источников**: основной, затем запасные озвучки по приоритету. Не скачалось нигде —
  статус `failed`, предупреждение в журнале, событие `voices.dub.changed`; следующий скан
  предлагает такую озвучку заново с основного источника. Серия, которой нет ни в одном источнике,
  фиксируется как `failed` с причиной.
- **Устойчивость**: записи `downloading` после перезапуска отправляются снова; готовый файл,
  пропавший с диска, скачивается заново; записи серий, вышедших из плана, удаляются; удаление
  сериала снимает загрузки, удаляет записи и временный каталог (`voices` — владелец каскада,
  отчёт `series.purged`).

### Р-41. Выравнивание серии и дорожки рядом с референсом (2026-10-28)

- **Постановка.** `conform.submit {ref, dubs, out_dir, cache_dir, label}` ставит серию в
  сервис выравнивания (`POST /conform/enqueue`); пути переводятся таблицей
  `conform.path_map` (по умолчанию `/nas` → `/mnt/meganas/media`). Ответ: `{job_id}`,
  `{rejected}` (окончательно: путь вне хранилища, отказ сервиса 4xx) или
  `{unavailable, retry}` (демон не настроен или недоступен — ждать `conform.daemon.up`;
  сбой в пути при живом демоне — повтор). Итог задачи — событие `conform.job.finished`
  (один раз на задачу), состояние задачи — `conform.job.get`.
- **Готовность серии.** Серия уходит одной задачей, когда референс на диске (триггер —
  `series.downloaded.changed`) и ни одна из её озвучек не скачивается и не выравнивается.
  Не скачавшаяся озвучка серию не задерживает; запоздавшая получает задачу отдельно.
  Временный отказ при живом сервисе повторяется с паузой 30 с, не более пяти раз на
  сериал, одна отложенная попытка на сериал.
- **Приёмка результата** (CHARTER, требование 7; **заменено Р-66**): дорожка принимается, если `ok`, нет
  `critical` и `suspect`, выходной файл существует. Иначе — `rejected` с причиной и
  предупреждением. Задача, завершившаяся ошибкой, переводит озвучки в `failed`
  (следующий скан предлагает их заново).
- **Раскладка.** Принятая дорожка переносится (копия во временный файл и замена) в каталог
  референса как `<имя видео>.<название озвучки>.ru.<расширение>`; статус `placed`, путь
  хранится в `voice_dubs.sidecar_path` (миграция 0017). Язык `ru` и расширение `.flac` —
  проверено в Jellyfin: дорожки показаны как «Русский · FLAC · Stereo · Внешние» с названием озвучки.
- **Уборка.** Когда все озвучки серии `placed`, `rejected` или `failed`, временный каталог
  серии удаляется, публикуется `voices.episode.settled`.
- **Восстановление.** После перезапуска задачи в состоянии `aligning` сверяются с сервисом
  (`conform.job.get`): итог применяется, забытая сервисом задача отправляется снова.
- **Каталог `_tmp`** сервиса рядом с референсом убирается, когда он пуст и у сериала нет
  идущих задач (находка 75).
- **Загрузчик потока** переведён на методику сервиса выравнивания (находка 74).

### Р-42. Дорожки следуют за референсом (2026-10-28)

- **Личность референса.** `voice_dubs.ref_uid` — медиа-элемент референса, по которому выровнена
  дорожка; `ref_path` — его файл (миграция 0018). Референс слота — файл на диске строки
  без `superseded_by`; пока победитель не скачан, референсом остаётся прежний.
- **Тот же элемент, другое имя или каталог** (переименование `renaming`, перенос `library`):
  дорожка переименовывается или переносится следом (в одном каталоге — `rename`, между
  каталогами — копия во временный файл и замена). Событие `voices.dub.changed` со статусом `moved`.
- **Другой элемент** (разрешение выше, референсом стала другая озвучка или источник):
  дорожки серии устарели с момента замены — удаляются из библиотеки вместе с выровненными
  и временными файлами, записи возвращаются к началу (`stale`), планирование озвучек
  запускается заново: озвучка, ставшая референсом, из дополнительных выпадает, прежняя
  озвучка референса становится дополнительной. Результат уже идущей задачи для прежнего
  референса игнорируется. Проверка совпадения таймлайна (сохранить совпавшие) не
  применяется; её можно добавить как оптимизацию через сервис выравнивания.
- **Серия вышла из плана и видео нет** — набор дорожек и записей удаляется (`removed`);
  видео есть — дорожки остаются. Удаление сериала удаляет записи и временные файлы,
  видео и дорожки остаются (принцип «удаление не удаляет файлы»).
- **Дорожка удалена пользователем** при живом видео — статус `rejected` («дорожка удалена»),
  заново не создаётся.
- **Сигналы.** `downloads.item.renamed` (новое), `library.relocation.finished` (успех),
  `series.downloaded.changed`, каждый скан (`voices.dispatch`).

### Р-43. Видимость озвучек по серии (2026-10-28)

- **Показ.** Во вкладке «Композиция» карточки серии web-источника: плашка на каждую
  дополнительную озвучку серии — «<озвучка>: <состояние>» (классы `pill` и `pill-danger`
  уже существующей карточки, дизайн не менялся). Состояния плашки — семь публичных состояний
  (Р-44); причина ошибки — во всплывающей подсказке плашки.
- **Доставка без опроса.** Первичное состояние — один запрос `GET /api/series/{id}/voices` при
  открытии вкладки; дальше — SSE `voice_dub_update`. Пакет несёт озвучку целиком
  (`voice_label`, `status`, `detail`), доспрашивать нечего. Тексты состояний — ключами каталога
  `voices.status.*`.
- **Состав события.** `voices.dub.changed` дополнен `voice_label` и `detail`; озвучка, которой
  нет ни в одном источнике, объявляется сразу при планировании. Промежуточное состояние
  «скачивается» событием не объявляется: первое видимое состояние — «скачана».



### Р-44. Семь состояний озвучки (2026-10-28)

- **Модель пользователя.** У озвучки семь состояний: **запланирована** (метаданные с сайтов
  получены, запись в БД есть и раскладка пройдена, действия не начаты), **в очереди на загрузку**
  (команда на загрузку отправлена, ждёт свободного места), **загрузка** (файл скачивается),
  **в очереди на выравнивание** (скачана и держится до референса и остальных озвучек серии, либо
  отправлена в сервис выравнивания и ждёт там), **выполняется** (выравнивается в сервисе),
  **готова** (дорожка лежит рядом с видео), **ошибка** (не скачалась, не прошла выравнивание,
  результат не принят, иное; причина — в подсказке и журнале). Очереди на загрузку и на
  выравнивание различаются: пользователь видит, в какой из них стоит озвучка.
- **Реализация.** Внутренние шаги (`pending`, `downloading`, `ready`, `aligning`, `aligned`,
  `placed`, `rejected`, `failed`) остаются для логики модуля; пользователю отдаётся `state`,
  выведенный из шага (`modules/voices/states.py`). `rejected` и `failed` — оба «ошибка».
  `voices.dub.changed` и `GET /api/series/{id}/voices` несут `state` рядом с `status`.
- **Загрузка.** Команда на загрузку объявляется сразу (`state` — «в очереди на загрузку»);
  «загрузка» наступает, когда `downloads` взял её из своей очереди и пошёл
  (`downloads.fetch.started`): у `downloads` свой лимит параллельных загрузок. Следующий источник
  озвучки после неудачи снова проходит «в очереди на загрузку». После перезапуска отправленные
  заново загрузки снова «в очереди на загрузку» до старта.
- **Выравнивание.** «В очереди на выравнивание» и «выполняется» в сервисе различаются по состоянию
  задачи демона: `voices` слушает `conform.queue.changed` и при смене состояния задачи объявляет
  озвучки заново; задача `queued` или `paused` — «в очереди на выравнивание», остальные —
  «выполняется». Без картины от демона — «в очереди на выравнивание».

### Р-45. Многодорожечная обработка: хвосты и устойчивость (2026-10-29)

- **Провайдеры с каталогом озвучек.** `BaseVideoProvider.has_voice_catalog` (по умолчанию `False`,
  у `dunhuatv` — `True`); запрос `sources.provider.info {url}` → `{provider, voices}` без сети. `voices`
  спрашивает его до разбора страницы. Новый провайдер подключается регистрацией и признаком.
- **Предел серий с временными файлами** (требование 12 CHARTER): настройка `voices.max_temp_episodes`
  (целое; 0 или пусто — без предела). Единая точка допуска `_admit` стартует ждущие загрузки порциями
  по числу серий: серия, уже начатая, берёт все свои озвучки, остальные «запланированы», пока серия
  не завершится (успехом или ошибкой всех озвучек) и не освободит место. Захват озвучки под загрузку
  идемпотентен (`claim_download`).
- **Отмена задачи в сервисе.** Команда `conform.cancel {job_id}` (`DELETE /conform/jobs/{id}`,
  best effort): задача, чей референс заменён, и задача удалённого сериала отменяются, итог не нужен.
- **Правила эквивалентности как данные (этап 9, первая версия).** Настройки `voices.aliases`
  (синонимы озвучек) и `voices.player_aliases` (синонимы плееров) — JSON-объекты {псевдоним:
  каноническое}; чистые функции получают `Equivalence`, а не глобальное состояние; мусор в настройке
  игнорируется. (Пары заменены группами `voices.groups`, Р-54.) Смена правил пересчитывает ключи
  озвучек: уже поставленные дорожки остаются под прежними ключами до замены референса.
- **Имена дорожек.** Две озвучки серии с одинаковым безопасным названием получают разные имена
  (`<название> 2`); сверка имён их не переставляет.
- **Устойчивость.** Гонки по находкам 77–78; серия, провалившаяся целиком, убирает временные файлы и
  освобождает место (раньше после неё не было прохода уборки). Проверено нагрузочными тестами: 12 серий
  × 4 озвучки под пределом 3 серии, с перезапуском модуля посреди пути.
- **Автоскан.** Проход по расписанию (`scan.all.start`) и ручной скан web-источника одинаково
  посылают `voices.dispatch`; покрыто тестами.


### Р-46. Многодорожечная обработка: устойчивость, достоверность интерфейса, идентичность (2026-10-29)

Решения по замечаниям ревью этапов 0–9.

- **Перенос дорожки — журнал намерения.** Строка получает `move_from` и `sidecar_path` до перемещения
  файла; завершение переноса и сверка при старте исходят из этих полей (`_finish_move`). Состояние
  «файл переехал, запись не обновилась» не возникает; «файла нет ни там, ни там» — `failed` с причиной.
- **Очистка — журнал.** Каждое удаление файла или каталога, вызванное модулем, идёт через `_discard`;
  отказ записывается в таблицу `voice_cleanup` (миграция 0019) и повторяется на старте, при возвращении
  сервиса и при следующем проходе; «уже нет» — успех. Папки временных файлов берутся из путей,
  сохранённых в строках, а не из настроек на момент уборки. Запись журнала, чей путь
  (или каталог над ним) снова числится за живой озвучкой, снимается без удаления.
- **Процессы и хранилище с пределом жизни.** `core/proc.py` (запуск с таймаутом и убийством процесса при
  отмене), `core/ffprobe.py` (проба длительности для `downloads`), `core/storage.py`
  (отдельный пул потоков и таймаут на файловые вызовы). Все короткие запросы к внешним программам
  (`ffprobe`, `yt-dlp --print`) идут через `run_capture`.
- **Постановка в сервис — по ключу.** Строки получают ключ до отправки и состояние «выравнивание» без
  номера задачи; ключ входит в метку задачи сервиса. Потерянный ответ разрешается запросом
  `conform.job.find {key}`: найдена — привязывается, не найдена — отправляется заново, сервис
  недоступен — ничего не отправляется. Отмена — запрос `conform.cancel → {done}`; несостоявшаяся отмена
  записывается в журнал очистки (вид `job`).
- **Длина дорожки не сверяется.** Выход выравнивания — эталон синхронизации; приёмка опирается на
  результат пары: `ok`, `suspect`, `critical` (**заменено Р-66**: вердикт — один `ok`). Несогласованная пара (разные видео под одним номером
  серии) приходит от сервиса как `ok=false` с текстом ошибки и становится `rejected`.
- **Интерфейс видит то же, что БД.** О каждой записи строки озвучки сообщается событием, включая создание
  запланированной строки, исключение из плана и удаление сериала. События несут `rev` (счётчик внутри
  запуска) и `epoch` (номер запуска, см. Р-50); интерфейс оставляет пакет с большей парой, удалённую озвучку запоздавший
  пакет не возвращает. При подключении клиента SSE `voices` публикует снимок всех озвучек
  (`voice_dubs_snapshot`, `rev` взят до чтения БД); компонент композиции озвучки по HTTP не запрашивает,
  `GET /api/series/{id}/voices` оставлен для диагностики.
- **Идентичность серии в каталоге CVH.** Если у озвучки один номер серии встречается в разных сезонах,
  каталог CVH отклоняется с причиной (сезоны не различаются); каталоги с различными номерами серий
  работают как прежде. Поддержка нескольких сезонов в одном сериале — вне этапов 0–9.
- **Настройки и ключи.** Настройки `voices.*` читаются одним запросом и разбираются в
  `modules/voices/settings.py`; неверное значение заменяется умолчанием и один раз пишется в журнал.
  Папка постановки и путь выровненной дорожки выводятся из пути скачанного файла, не из настроек и не из
  карты путей сервиса. Если изменённые правила дали голосу новый ключ, его строки сохраняют прежний
  (`_adopted_keys`): размещённые дорожки не превращаются в новый голос.
- **Причины — коды.** `detail` в событиях, снимке и HTTP — `{code, params}`; слова собирает интерфейс по
  ключам `reason.*` (Р-48); слова чужих систем (загрузчик, сервис выравнивания) — код `external` с
  `params.text`. Тест сверяет коды модуля с каталогом. Храповик `tests/test_ui_literals.py`: число
  русских литералов в экранах не растёт.
- **Явные отступления.** Докстринги новых модулей — English, добавления в прежние модули — язык файла;
  комментарий `.env.example` — русский, как весь файл; плашки озвучек — элементы с уже существующими
  классами в существующем компоненте.

### Р-47. Границы расширения и контракты между модулями (2026-10-29)

Решения по замечаниям ревью о размазанных правилах и несверяемых описаниях данных.

- **Общие описания данных — `core/contracts`.** Статусы строки озвучки (`DubStatus`), статусы события
  (`DubEventStatus`), состояния для пользователя (`DubState`), подсказки (`DubHint`), роли раскладки —
  перечисления; событие, снимок, запись, раскладка, источник релиза (`ReleaseSource`), разбор релиза
  (`Release`), итог задачи выравнивания (`AlignmentJob`, `DubResult`) — модели. Модуль импортирует их из
  `core`, не из соседа. Производитель строит сообщение моделью, потребитель читает ею же.
- **Граница провайдера.** Модуль `sources` проверяет разбор любого провайдера моделью `Release`; разбор не по
  контракту — ошибка с понятным сообщением, а не молчаливое искажение. Общий набор проверок
  `tests/provider_contract.py` вызывается в тестах каждого провайдера.
- **Типы интерфейса — из схемы API.** Gateway отдаёт эти модели в ответах и в схеме (вместе с пакетами потока
  событий `DubEvent`, `DubsSnapshot`); стор, карточка и форма добавления используют сгенерированные типы.
  Подсказку для состояния называет ядро (`hint`), ветвления по статусу в компоненте нет.
- **Переходы состояний — одна таблица.** `modules/voices/lifecycle.py` перечисляет переходы строки и наборы
  состояний (`WORKING`, `FINAL`, `HOLDS_FILES`, `WAITS_FOR_REFERENCE`); репозиторий пропускает запись только
  из состояний, которые перечисляет переход, и пишет в журнал промах не-оспариваемого перехода. Названий
  статусов в SQL и в модуле строками нет.
- **Сервис выравнивания — один адаптер.** `modules/voices/alignment.py` знает папки (`_aligned`, `_cache`,
  `_tmp`), сопоставление результата с озвучкой по имени файла, путь выровненной дорожки и допуск результата
  по вердикту сервиса.
- **Форма выдачи — стратегия.** Контракт `Output` (`destination`, `exists`, `deliver`, `follow`, `settle`,
  `remove`) в `modules/voices/outputs.py`; дорожка рядом с видео — `SidecarOutput`. Журнал очистки различает
  виды `path`, `tree`, `artifact`, `job`. Колонка `sidecar_path` переименована в `output_path` (миграция 0020).
  Другая форма выдачи (контейнер для Plex) — другой класс с теми же операциями; сквозной тест с второй формой
  выдачи не меняет код модуля.

### Р-48. Причины — один формат на всю систему (2026-10-29)

Решение по остатку замечания о текстах: причины недоступности и отказа провайдеров были русскими
предложениями серверной части.

- **Формат.** Причина — код и факты: JSON-строка `{"code": ..., <факты>}` (`core/reasons.py`: `reason`,
  `parse`, `describe`). Текст, который не является такой строкой (слова чужой системы, запись, сделанная до
  перехода на коды), показывается как есть. Факт может быть списком или вложенной причиной.
- **Одна граница в интерфейсе.** `web/src/lib/reason.ts` (`reasonText`) принимает причину в виде объекта
  `{code, params}` или строки, подставляет факты в слово из каталога `reason.*` и разворачивает вложенные
  причины. Через неё идут причина озвучки, отчёт о плеерах в окне добавления и в карточке серии, текст
  ошибки ответа API.
- **Производители.** Все причины и сообщения исключений стека видео-провайдеров (`dunhuatv`, `cdnvideohub`,
  `kodik`, `ruchime`, `players`, `vibix`) строятся через `reason(...)`; слова — ключи каталога. Вне формата
  остаются названия, входящие в данные (заглушка `без студии`, подписи серий «N серия»), и сообщения
  журнала.
- **Проверка.** `tests/test_reasons.py` сверяет коды всех модулей с каталогом; храповик
  `tests/test_ui_literals.py` затянут: литералы блоков отчёта о плеерах заменены ключами.

### Р-49. Неизменность DOM относилась к переезду и снята (2026-10-29)

Правило «дизайн, DOM и классы неприкосновенны» появилось в первых правилах переписывания как условие

### Р-50. Второй круг ревью: устойчивость, версии, постановка (2026-10-29)

- **Событие — из записанного.** `_announce` читает строку после записи и строит событие из неё; версия берётся
  до чтения. Раздельных «записать статус» и «объявить статус» с разными источниками правды нет.
- **Результат одной озвучки не рушит пакет.** Успех без файла — отказ `output_missing`; обработка результата
  каждой озвучки изолирована, сбой даёт `result_unreadable` только ей.
- **Возобновление — по незавершённой операции.** `series_with_open_work`: серия возобновляется, если у неё есть
  озвучка, ждущая референс, или начатая и не завершённая операция, каким бы ни был статус озвучки.
- **Сезоны.** Номер серии, общий для разных сезонов где угодно в плейлисте CVH, отклоняет каталог.
- **Исход постановки — четыре значения.** Принято, отклонено, не отправлено, исход неизвестен. При неизвестном
  исходе ключ задачи сохраняется и спрашивается `conform.job.find`; «не отправлено» — только отказ до отправки
  запроса (нет настройки, демон не поднят, ошибка соединения).
- **Постановка хранит каталог результата.** `voice_dubs.out_dir` (миграция 0021): результат ищется там, куда
  его просили положить, независимо от настроек и корней отдельных озвучек.
- **Порядок пакетов — запуск и счётчик.** `epoch` (таблица `voice_epoch`, миграция 0022) растёт при каждом запуске
  `voices`, `rev` считает пакеты внутри запуска; интерфейс упорядочивает по паре и принимает снимок более
  позднего запуска как новый авторитетный. Событие показывает строку такой, какая она при объявлении:
  быстро следующие друг за другом шаги могут быть показаны последним из них.
- **Владение путём до конца вызова.** Изменяющий вызов хранилища называет свои пути (`owns`); они заняты, пока
  не вернулся поток. Таймаут ожидания — «исход неизвестен» (`StorageTimeout`), а не разрешение занять имя.
- **Раскладка папок демона — в мосте.** Имена папок результата, кэша и рабочей папки знает только `conform`

- **`Output` — четыре операции.** `destination`, `exists`, `settle`, `remove`; операции, которых оркестратор не
  вызывает, убраны. Выход уровня серии (контейнер) — отдельный контракт будущего этапа.
- **Язык комментариев.** Добавленные докстринги старых модулей и комментарий `.env.example` — английские;
  исключения «по языку файла» нет.

### Р-51. Третий круг ревью: исходы, владение, восстановление, граница снимка (2026-10-29)

- **Удаление.** Сравнение времени изменения с часами сервера убрано. Имя охраняют владение (в полёте) и запись
  живой озвучки или папка идущей задачи (отложенная очистка); удаление подтверждается освободившимся именем и
  кончается «имя свободно» или «в журнале».
- **Удаление ненужного файла — одно место.** `core.storage.remove_file`/`discard`: отказ называется в журнале с
  путём и возвращается; молчаливое `except OSError: pass` у `os.remove` в коде запрещено охранным тестом.
- **Владение — до конца записи.** `core.storage.hold`/`acquire`: проверка и захват без ожидания между ними;
  владение длится, пока жив последний пишущий под ним; потоки `call` и программы `core.proc.spawn` прикреплены.
  Вызовы владельца собственные. Программы запускаются только через `core.proc`.
- **Исход постановки — фаза.** `DaemonRefused`, `NotDelivered`, `Unconfirmed` в клиенте; `SubmitReply` в
  `core/contracts` (accepted, rejected, unavailable, uncertain); не ясный ответ = неопределённый исход; у
  `job.get` недоступный демон — ошибка запроса, а не «задача исчезла».
- **Восстановление — свой счёт.** `Recovery`: обязательства `submission:`, `job:`, `cleanup:`, `series:`;
  пауза удваивается до потолка; сообщение владельцу после `SUBMIT_RETRIES` неудач; попытки не прекращаются.
  Подсказка `awaiting_answer` показывает отправленную озвучку без номера задачи.
- **Граница снимка в интерфейсе.** Хранилище озвучек держит последний принятый полный снимок и отвергает всё,
  что не новее его.
- **Объявление загрузки — до команды.** Событие «загрузка отправлена» публикуется до команды `downloads.fetch`.

### Р-52. Четвёртый круг ревью: поколения задачи, передача журналу, строгое чтение (2026-10-30)

- **Папки поколения.** Каждая постановка пишет в `<результат>/<ключ>` и `<кэш>/<ключ>`; папки создаёт приложение
  до отправки; итог читается из папки строки. Задача, не подтверждённая остановленной, не достаёт до итога новой.
- **Журнал вперёд.** Указатели строки, её задача (`job`) и отправка без ответа (`submission`) переходят в журнал
  очистки в одной транзакции со сбросом, удалением эпизода или серии, завершением эпизода; удаление, отмена и
  поиск по ключу выполняются только из журнала. `voice_cleanup.scope` — папка задачи; чистится после подтверждённой
  остановки (миграция 0023).
- **Чтение задачи строгое.** Успешный ответ проверяется (объект с нужным номером, список объектов с номерами);
  «задачи нет» — только `404`.
- **Обязательство при восстановлении номера.** Номер, найденный по ключу, регистрирует `job:<номер>`.
- **Планировщик не кончает обязательство.** Степень паузы ограничена, невычислимая пауза заменяется запасной.

### Р-53. Пятый круг ревью: пересекающиеся области владения, версия записи, отправка в пути (2026-10-30)

- **Удаление ждёт все пересекающиеся области.** `_contested`: папки идущих задач живых строк и записи журнала о
  задачах и отправках с папкой, не подтверждённых остановленными; место, вложенное и вышестоящее.

  версию; `cleanup_done(путь, версия)`; ошибка попытки версию не меняет.
- **Отправка в пути.** Ключ помнится, пока исход не разобран; поиск по ключу и восстановление до этого записи не
  кончают и озвучки не шлют; принятая задача для ушедших озвучек отменяется.

### Р-55. Шапка и нижняя панель модальных окон подстраиваются под место (2026-10-30)

- **Причина поломки.** Подписи вкладок шапки схлопывались по порогу ширины экрана (1000 px), подобранному под шесть
  вкладок; с седьмой («Озвучки») полоса вкладок не помещалась и выталкивала крестик, на узком экране шапка
  выходила за окно. Название окна не сжималось вовсе.
- **Решение в общей оболочке `ModalShell`.** Оболочка сама меряет, помещаются ли вкладки: сначала плотнее отступы
  (`tabs-tight`), потом подписи невыбранных вкладок в иконки (`tabs-compact`), потом и подпись выбранной
  (`tabs-icons`), и если не помещаются иконки, полоса прокручивается, выбранная вкладка возвращается в видимую часть.
  Вкладки сжимаются раньше названия (коэффициент 100 против 1), название обрезается последним, крестик виден всегда.
  Порог по ширине экрана убран, действует во всех окнах с вкладками.
- **Нижняя панель** переносит кнопки на вторую строку, когда они не помещаются.

### Р-56. Память отключённых серий действует и для сайтовых источников (2026-10-30)

### Р-57. Сервер выравнивания в настройках, карточки очереди и остановка потока (2026-10-30)

- **Адрес демона и карта путей — настройки.** `conform.url` и `conform.path_map` хранятся в таблице настроек. `ST_CONFORM_URL`
  остаётся значением по умолчанию, пока `conform.url` не сохранён; сохранённое значение, в том числе пустое, главнее
  переменной. Запросы `conform.settings.get` и `conform.settings.set` (проверка целиком, коды причин
  `conform_url_invalid`, `path_map_empty`, `path_row_incomplete`, `path_not_absolute`, `path_duplicate`), событие
  `conform.settings.changed` → SSE `conform_settings_update`, эндпоинты `GET/PUT /api/conform/settings`. Новый адрес
  применяется без рестарта: лента демона переподключается, картина очереди начинается заново.
- **Экран.** Блок «Сервер выравнивания» во вкладке «Авторизация», последним блоком после TMDB: адрес, рабочая папка здесь и на демоне, индикатор
  демона. Сохраняется кнопкой вкладки вместе с остальными подключениями; пишется только при изменении.
- **Карточки очереди.** Озвучка называется своим названием: события озвучек (`voices.dub.changed`,
  `voices.dubs.snapshot`) несут `job_id` и `file`, экран сопоставляет их с результатом задачи; без совпадения показывается
  имя файла без расширения. Имя файла озвучки задаёт одна функция `dub_file`. Заголовок задачи без ключа постановки:
  `conform` отдаёт `label` (человеческая часть) и `key`.
- **Индикатор демона.** Цветные варианты пилюль (`pill-success`, `pill-info`, `pill-danger`, `pill-primary`,
  `pill-secondary`) и строка `.queue-row` — общие стили, раньше они действовали только внутри карточки. Индикатор — три
  пилюли (состояние, версия, устройство), переносятся на узких экранах.
- **Остановка.** Поток `/api/stream` завершается по сигналу остановки (SIGINT, SIGTERM): рестарт не ждёт предохранитель
  uvicorn и не пишет ошибку. Предохранитель `--timeout-graceful-shutdown` остаётся.
- **Схема API.** Маршруты с несколькими методами регистрируются отдельным маршрутом на метод (`route_per_method`): имена
  операций уникальны и не зависят от порядка множества.

### Р-58. Рабочая папка конформа: два значения в настройках, демон видит только её (2026-10-30)

- **Правило.** В коде нет ни одного пути хранилища; сторож `tests/test_no_hardcoded_paths.py` падает на строковый путь вида
  `/nas`, `/mnt`, `/media`, `/srv`, `/data`, `/tmp`, `/home`. Значений по умолчанию нет.
- **Две настройки, хозяин — мост `conform`.** `conform.work_dir` (рабочая папка так, как её называет этот сервер) и
  `conform.work_dir_remote` (та же папка так, как её называет демон); их вводит владелец в блоке «Сервер выравнивания»
  вкладки «Авторизация». Прежняя карта путей `conform.path_map` и `voices.temp_root` не используются. Проверка при
  сохранении: при заданном адресе обе папки обязательны, обе абсолютные, папка здесь не вершина хранилища (корень или
  точка монтирования).
- **Две подпапки с фиксированными именами:** `downloads/` (скачанные озвучки ждут выравнивания) и `conform/` (папка работы
  сервиса). `conform.workspace {}` отдаёт обе, пусто, пока папка не названа; озвучки получают свою папку у моста.
- **Демон видит только рабочую папку.** Перед отправкой задачи референс копируется в
  `conform/<сериал>/<серия>/_ref/<ключ>/` (обычная копия, шаг очереди серии), результат и кэш пишутся в соседние папки
  того же ключа. Задача не ушла (демон недоступен) — копия удаляется; серия завершена, удалена или выпала из плана —
  вся папка серии в `conform/` убирается тем же журналом уборки, что и озвучки. Готовую дорожку рядом с видео в папке
  сериала переносит наш сервер.
- **Имена файлов уникальны:** озвучка `<номер сериала>_sNNeNN_<ключ озвучки>.mp4`, копия референса
  `<номер сериала>_sNNeNN_ref.<расширение>`.
- **Пусто — безопасно.** Рабочая папка не названа: озвучки не записываются и не скачиваются, задание на выравнивание не
  отправляется (`conform_no_work_dir`), в журнале причина.
- **Убрано.** Очистка временной папки рядом с видео библиотеки (демон её там больше не создаёт); временный каталог провайдера
  манифестов берётся у системы.

### Р-59. Очередь выравнивания: удаление, график, жизненный цикл папки результата (2026-10-30)

- **Карточка задачи.** Заголовок — сериал и серия; озвучки строками (название из конструктора правил, остаток и покрытие,
  вердикт «принята» / «отклонена» по тому же правилу, что у приёмки результата); у идущей задачи полоса прогресса с этапом;
  внизу время выполнения (у ждущей — время добавления) и номер задачи. Тексты ошибок в карточку не выводятся: они в журнале.
- **Кнопки.** «Отменить» у задачи, которая ждёт, идёт или на паузе: демон останавливает её, запись остаётся «отменено».
  «Удалить» у завершённой: запись уходит из истории демона вместе с файлами, которые он держит для записи (график, журнал,
  карта времени, кэш; выходной звук остаётся). Эндпоинт `DELETE /api/conform/jobs/{job_id}`, запрос шины `conform.cancel`.
  Ручной постановки задачи нет: задачи создаёт модуль озвучек.
- **График.** Демон отдаёт PNG озвучки (`/conform/plot/<задача>/<имя>`); результат озвучки несёт имя картинки (`plot`),
  кнопка «График» открывает её в окне поверх страницы, не во вкладке: вписанной в окно или в натуральном размере.
  Картинка идёт через наш сервер: `GET /api/conform/jobs/{job_id}/plot/{name}`, запрос шины `conform.plot`; допускается
  только простое имя `*.png`.
- **Жизненный цикл папки результата** (`<папка серии>/_aligned/<ключ задачи>`: отклонённая дорожка, график, статистика).
  Принятую дорожку модуль озвучек переносит рядом с видео. Папка живёт, пока запись задачи есть в истории демона: график
  открывается оттуда. Запись уходит — демон снимает свои файлы, мост шлёт `conform.job.removed`, модуль озвучек убирает
  папку и пустые папки вокруг. Запись, ушедшая, пока модуль не слушал, находится запросом `conform.job.get` (статус `gone`)
  при появлении демона и при завершении серии.
- **Завершение серии** убирает только своё: скачанные озвучки и копию референса. Событие `voices.episode.settled` больше не
  означает, что рабочая папка серии убрана целиком.
- **Что удаляет запись само.** Замена референса, выпавшая серия и удаление сериала передают в журнал уборки задачи любой
  стадии (прежде — только выполняющиеся): демон снимает записи, папки результата убираются.
- **Настройка «Очищать очередь выравнивания по завершении»** (`conform.clear_finished`, «true» или «false»; флаг в
  группе «Параметры конвейера» вкладки «Отладка» рядом с остальными флагами, `GET|POST /api/settings/conform_clear_finished`,
  по умолчанию выключена): серия завершена и результат принят — задачи серии передаются в журнал уборки, запись уходит из
  истории, папка результата убирается. Выключена — записи копятся, их удаляет владелец кнопкой. Включение не затрагивает
  записи, уже лежащие в очереди.

### Р-60. Ruchime: выбор сезона Vibix и отключение плееров в адресе сериала (2026-10-30)

- **Причина.** Каталог Vibix один на несколько релизов и состоит из сезонов с повторяющимися номерами серий; страница релиза
  не называет, какой сезон ей принадлежит. Серия искалась по одному номеру, скан и загрузка выбирали её по-разному, поэтому
  скачиваться могла серия чужого сезона. Автоматического способа связать релиз с сезоном нет: выбор делает владелец.
- **Адрес сериала несёт выбор** (как у dunhuatv.ru): `<страница релиза>?vibix=<позиция сезона в каталоге, с 1>&off=<плееры
  через запятую>`. Пока ничего не выбрано, адрес прежний. Один сезон в каталоге выбора не требует.
- **Привязка при скане.** Серия страницы N берёт серию N выбранного сезона. Несколько сезонов без выбора и выбор несуществующего
  сезона делают Vibix не кандидатом; причины `vibix_season_required` и `vibix_season_missing` видны в отчёте о плеерах.
- **Адрес кандидата Vibix** — `<страница серии>#vibix=<сезон>/<серия>`: загрузка берёт ту запись каталога, которую проверил
  скан; записи другого сезона не подставляются. Ссылка прежнего вида (без фрагмента) разрешается только при одном сезоне.
  У существующих кандидатов Vibix меняются адрес и `unique_id`.
- **Отключённый плеер** (`off`) не опрашивается и не считается; причина `source_disabled`. Если отключены все плееры,
  страницы серий не читаются.
- **Раскладка источников.** Запрос шины `sources.video.layout {url}` → `{sources, selected_source, reason}`; признак
  `has_layout` в ответе `sources.parse` говорит, что спрашивать есть у кого. Каталог читается браузером, поэтому раскладка
  отделена от разбора. Сезон каталога — источник: `url` (адрес с этим выбором), `player: vibix`, `studio` (название сезона
  как его дал каталог), `first/last/count/ranges/episodes` и `resolutions` (разрешение серий диапазонами). Разбор ruchime
  отдаёт `players[имя].enabled` и `players[имя].toggle` (адрес с обратным состоянием плеера).
- **Покрытие плееров.** Запрос шины `sources.video.coverage {url}` → `{players, reason}` читает страницы всех серий и пробует каждый
  плеер страницы на каждой серии, где он есть (скан этого не делает: он пропускает плеер ниже уже достигшего потолка). По плееру:
  `present`, `available`, `count`, `ranges`, `resolutions` (разрешение серий диапазонами). Ответ не зависит от выбора в адресе: читается один раз на страницу, отключённый
  плеер окно лишь прячет. Нечитаемая страница серии даёт `reason` без частичного ответа. Прогресс — событие `sources.coverage.progress {url, current, total, phase,
  active}` (SSE `coverage_progress`, ключ — адрес страницы релиза), отдельное от прогресса скана; у запроса свой замок, чтобы долгое
  чтение не задерживало разбор и скан того же сайта. Эндпоинт `POST /api/web_video/coverage`.
- **Общее чтение с сканом.** Что прочитало покрытие (страницы серий и пробы плееров страницы), провайдер держит 15 минут, и скан
  сразу после добавления берёт серии оттуда, не читая их заново; кэш учитывает отключённые плееры адреса, а серию, у которой проба
  закончилась временным отказом, скан читает заново.
- **Неуверенный ответ плеера.** Отказ хоста (403, 408, 425, 429, 5xx, нет ответа) и страница без признаков видео не означают, что
  серия не играет: проба повторяется один раз через 3 секунды и только потом записывается как недоступность. Правило одно для
  быстрого отчёта разбора, первого захода скана, каскада скана и покрытия (`RuchimeProvider._probe_settled`).
- **Допущение.** Номер серии страницы совпадает с номером серии выбранного сезона. Релиз со сквозной нумерацией по нескольким
  сезонам каталога этим выбором не покрывается.

### Р-61. Парсеры сайтов собирают таблицу релиза; плееры общие, политика одна (2026-10-30)

- **Причина.** Чтение сайта шло двумя путями (скан и покрытие), повторы и паузы были реализованы в пяти местах, разбор ответа плеера
  был смешан с сетью и решением о повторе, VK существовал в двух несвязанных реализациях. Ответ VK «оболочка сайта вместо плеера»
  записывался как отсутствие видео.
- **Решение.** Парсер сайта сам строит один раз по запросу таблицу релиза «серия × плеер → клетка». Из неё берутся все ответы
  шины и представления (диапазоны, разрешения, выбор лучшего для скана, `layout`, `coverage`). Плееры — общие модули
  `modules/sources/players/` с контрактом `find / fetch / read / resolve`; `read` — чистая функция с закрытым набором видов.
  Повторы, паузы, предел времени и число запросов на хост — только в `modules/sources/policy.py`.
- **Схема.**
  ```
  шина: sources.parse / layout / coverage / video.scan / video.stream
     │
  парсер сайта (ruchime, dunhuatv) — логика сайта
     │  по запросу строит ОДНУ таблицу релиза: серия × плеер → клетка
  таблица релиза ── представления (чистые функции): диапазоны, разрешения, выбор лучшего, layout, coverage
     │  клетки заполняет
  политика — единственное место попыток, пауз, пределов времени и числа запросов на хост (core/retry.py, sources/policy.py)
     │  вызывает
  плееры (players/: vk, allvideo, vibix, kodik, cdnvideohub) — общий контракт
  ```
  Зависимости направлены вниз: `provider → table → policy → players`. Плеер не знает ни политики, ни парсера; политика знает только
  контракт плеера; таблица не знает конкретных плееров.
- **Раскладка.** `modules/sources/policy.py`; `players/` (`contract.py`, `http.py`, `vk.py`, `vk_files.py`, `vk_show.py`, `allvideo.py`,
  `vibix.py`, `vibix_protocol.py`, `kodik.py`, `cdnvideohub.py`); `video_providers/` (`base.py`, `registry.py`, `ranges.py`, `table.py`,
  `views.py`, `players.py` — порядок плееров ruchime; `ruchime/` — `provider.py`, `site.py`, `address.py`; `dunhuatv.py`).
- **Контракт плеера.** `find(текст страницы)` — чистая функция; `fetch(ссылка)` — один запрос без повторов; `read(ответ)` — чистый разбор в один
  вид из закрытого набора (играет с разрешениями, не найдено, закрыто, не плеер, ошибка статуса); `resolve(ссылка)` — поток перед загрузкой.
  Клетка таблицы: окончательный вид, разрешение, число попыток; если попытки или время вышли, клетка — «не получено», а не «нет».
- **Требования.** Разбор ответа — чистая функция без сети, времени, состояния и повторов. Повторы, паузы, пределы — в одном месте. Страница серии
  читается один раз, плеер на серии пробуется один раз; пока таблица релиза собирается, остальные запросы шины ждут её завершения и сайт не
  читают; готовая таблица живёт в памяти ограниченное время. Недоступные серии отражаются диапазонами по каждому плееру; серии без ответа
  за отведённые попытки считаются отдельно от серий, которых у плеера нет. VK, AllVideo, Vibix, Kodik и cdnvideohub реализуют один контракт.
- **Порядок внедрения (рамки этапа 9 приёмки).** Шаг 1: плееры на общем контракте и единая политика — сделано (VK, AllVideo, `core/retry.py`).
  Шаг 2: таблица релиза в парсере ruchime — сделано (скан, `layout`, `coverage` читают из неё; чтение страниц — `ruchime/site.py` на `AdaptivePacer` и
  `core/retry.py`; копии повтора и темпа удалены; сторож `tests/test_retry.py` охватывает пакет `ruchime/`). Шаг 3 — сделано:
  Vibix, Kodik и cdnvideohub — плееры контракта (`players/`), dunhuatv читает страницу и каталоги через `policy.ask`, опрашивает серии через
  таблицу и `settle`, поток берёт из файлов чтения; `table.py` и `views.py` общие для парсеров; `video_providers/retry.py` удалён. Серия, ответ
  которой не получен до конца, в dunhuatv — «не подтверждено», а не отказ всего скана; отказ остаётся, когда не получена ни одна серия. Шаг 4 — сделано: охват плеера несёт `unavailable` (плеер показывает серию, но не играет её) и `not_obtained` (ответ не получен до конца) диапазонами; окно добавления показывает их строками «Недоступно» и «Не получено» под разрешениями плеера. Каждый шаг заканчивается рабочим приложением, тестами и проверкой на живых данных.
- **Заменяет** в Р-60 абзац «Неуверенный ответ плеера» (повтор одной пробы через 3 секунды) и поле `unverified` покрытия; их
  место займёт клетка «не получено» таблицы.
- **Не меняется.** Адрес сериала с выбором сезона и отключением плееров, поведение шины и контракты эндпоинтов до этапа 12.

### Р-62. Тело задачи выравнивания сверяется со схемой демона (2026-10-30)

- **Причина.** Схема `POST /conform/enqueue` демона запрещает лишние поля и больше не содержит `cache_dir`, а мост слал его по прежнему
  описанию контракта: любая постановка отвергалась кодом 422 (`daemon_refused`), озвучки серии оставались в ошибке.
- **Решение.** Клиент демона один раз читает `/openapi.json`, берёт поля схемы тела `ConformEnqueueBody` и отправляет только их
  (`accepted_fields`); при нечитаемой схеме или схеме, допускающей лишние поля, тело уходит как есть. Знание сбрасывается при запросе
  сведений о демоне (возвращение демона после обновления) и повторяется, пока схема не прочитана.
- **Не меняется.** Контракт шины `conform.submit {ref, dubs, out_dir, cache_dir, label, key}` между озвучками и мостом.

### Р-63. VK читается прямым запросом, а в загрузку идёт прямая ссылка (2026-10-30)

- **Статус: заменено Р-64.** Вызов страницы ролика отказывает роликам, которые открываются только по ключу плеера; решения о
  единственном входе и о загрузке по прямой ссылке не действуют.
- **Причина.** VK выдаёт встроенному плееру (`video_ext.php`) по случайному выбору одну из двух страниц: прежнюю, где данные лежат в самой
  странице, и новую, которую браузер достраивает скриптами (заголовок `VK`). Разбор по HTML читал только первую, вторую считал отсутствием
  видео; штатный yt-dlp на ссылке плеера давал «Unable to extract player params». Готовый адрес mp4 с заголовками уводил загрузку в одну
  ветку ffmpeg одним потоком: серия 2160p (1170 МБ) скачивалась 1032 секунды.
- **Решение.** Плеер VK делает только запрос, стоящий за прямой ссылкой `vk.com/video<oid>_<id>`: `POST vk.com/al_video.php` (`act=show`,
  `video`, `al=1`, заголовок `X-Requested-With`). Ответ не зависит от вида страницы: `payload` = `[код, элементы]`, параметры плеера
  (`url144…url2160`, `hls`, `dash*`) в последнем элементе, ошибки с кодом 8 и словами («была удалена», «Ошибка доступа», «Доступ
  ограничен»). Чистое чтение — `players/vk_show.py` (`read_show`). Страница плеера и готовый адрес потока для VK не используются.
- **В загрузку идёт только `https://vkvideo.ru/video<oid>_<id>`.** Разрешение (в том числе потолок для дорожек, которые не референс) и
  способ загрузки выбирает разбор самого yt-dlp, центральный модуль `downloads` качает параллельными фрагментами по умолчанию. Видео,
  которое прямой запрос не открывает, кандидатом VK не становится; серию берут другие плееры (AllVideo, Vibix).
- **Проверено.** yt-dlp на прямой ссылке прочитал 14 из 14 серий там, где на ссылке плеера 0 из 14; плеер: 14 из 14 (2160p) пачкой и поштучно;
  та же серия скачивается за 115 секунд вместо 1032; из 51 боевого ролика ruchime прямой запрос открывает 41, 10 отвечают «Доступ ограничен»
  (все уже скачаны).
- **Не меняется.** Кандидаты (`vk.com/video…`, от них зависит идентификатор элемента), порядок плееров, VK-каналы.

### Р-64. VK читается так же, как плеер сайта; готовый файл качается кусками по Range (2026-10-30)

- **Причина.** Часть роликов (серия «Континент силы и духа» 125, 126, 128–134) открывается только по ключу `hash` из ссылки плеера:
  вызов страницы ролика (`al_video.php`) и yt-dlp по прямой ссылке отвечают им «Доступ ограничен», страница встроенного плеера и
  `video.get` с ключом отдают файлы 144…2160p. Единственный вход Р-63 считал такие серии закрытыми. yt-dlp не открывает их ни по ссылке,
  ни по адресу плеера (разбор VK в yt-dlp 2026.10.26 тот же).
- **Решение. Входы VK по порядку:** (1) `POST api.<домен>/method/video.get` с `videos=<oid>_<id>_<hash>`, `is_embed=1`, `ref_domain=<сайт>`
  и токеном, который выдаёт страница плеера (`webToken`, домен API из белого списка), пачки до 50; (2) данные самой страницы плеера
  (`apiPrefetchCache`, `playerParams`, голые литералы только при отсутствии собственных данных страницы); (3) вызов страницы ролика
  как ещё один источник файлов. Чистое чтение — `players/vk_files.py`.
- **Вердикт по серии.** Доступна — любой вход отдал файлы. Закрыта — только явный отказ про это видео: код 15 или 204 `video.get`, `content_restricted`,
  `restriction.can_play = 0` либо отказ, напечатанный страницей плеера. Всё остальное (нет токена, 429, обрыв, незнакомый вид страницы) —
  «не удалось узнать»: серия повторяется по политике, закрытой не считается. Отказ вызова страницы ролика закрытием не является.
- **Токен.** Живёт в памяти и привязан к клиенту, которому выдан; хранится до срока, названного страницей (иначе 300 с); отклонённый
  токен берётся один раз заново, пачка повторяется. Ищется в страницах первого, среднего и последнего плеера под двумя User-Agent.
  Страница плеера приходит в двух видах: прежнем, где файлы лежат в странице и токена нет, и оболочке с токеном; читаются оба.
- **Загрузка.** В запись серии (`download_url`) идёт адрес плеера с ключом. При загрузке провайдер берёт свежий адрес файла нужной высоты
  (подписанные адреса не хранятся) и отвечает `sources.video.stream` с `progressive: true`; модуль `downloads` качает готовый файл кусками
  одновременно по HTTP Range (`downloads/ranged.py`), без Range — одним потоком через ffmpeg. yt-dlp для таких адресов не вызывается.
- **Проверено на живых ответах.** «Континент силы и духа», 226 серий: VK 224, закрыты 127 и 207 (диапазоны `1-126, 128-206, 208-226`); 208 серий
  в 2160p и 16 в 1080p. Прежний вид страницы: 12 из 12 запросов под двумя User-Agent без токена, файлы из страницы. Оболочка с токеном:
  пачка из 12 ключей (9 серий «только по ключу» и 3 открытых) — 12 из 12 с 8 файлами. Серия 125 через приложение (разбор, правило, сериал,
  скан, загрузка): 2160p h264, 416 МБ за 8 с; файл 720p той же серии — 116,5 МБ за 2,2 с (около 52 МБ/с).
- **Не меняется.** Кандидаты (`vk.com/video…`, от них зависит идентификатор элемента), порядок плееров, VK-каналы (`modules/sources/vk.py`).
- **Установлено.** yt-dlp отвечает 400 на адрес hls, который отдают страница плеера и `video.get`, со своим User-Agent браузера и читает его (форматы 144…2160p) с `--user-agent Mozilla/5.0`; httpx и ffprobe читают адрес без заголовков. В загрузке VK yt-dlp не используется: нарезка по Range даёт около 52 МБ/с против 14 МБ/с у параллельного hls.

### Р-65. Повторы запросов решаются в одном месте: `core/retry.py` (2026-10-31)

- **Причина.** В модуле загрузок повтор и паузы решались четырьмя циклами разного вида: проба длительности (3 попытки, 2 с), части файла при загрузке
  кусками (3 попытки, 1 и 3 с), две копии повтора задачи загрузки (3 попытки, 5 с). Единая политика была только у плееров источников
  (`sources/policy.py`), а модуль загрузок импортирует только `core`.
- **Решение.** Бюджет (число попыток, паузы, предел времени, `Retry-After`, `UNTIMED` для бюджета без предела) и цикл `retrying` лежат в `core/retry.py`.
  Политика плееров (`settle`, `Pacer`, виды неуверенных ответов) стоит на нём; проба длительности, части файла и оба повтора загрузки берут тот же бюджет.
  Числа остаются константами своего места (`PROBE_*`, `PART_*`, `MAX_DOWNLOAD_ATTEMPTS`, `RETRY_DELAY_S`), цикл и расчёт паузы — один.
- **Сторож.** `tests/test_retry.py`: в модуле загрузок, плеерах и политике нет цикла попыток; пауза в них всегда из бюджета; класс `Budget` вне `core` не определён.
- **Модуль торрентов.** Повторы запросов клиента qBittorrent (`qbt_client.py`: запрос, поиск infohash) и ожидания состояния в модуле
  (метаданные, файлы предпросмотра, уборка предпросмотра) идут через `retrying`; недостижимый `sync_maindata` удалён. Периодические
  мониторы конвейера и загрузок ждут по таймеру по определению и под сторож не попадают; сторож `tests/test_retry.py` охватывает
  `qbt_client.py` целиком и циклы попыток в `module.py`.
- **Не входит.** Копии повтора и темпа чтения страниц ruchime и `video_providers/retry.py` удалены шагами 2 и 3 внедрения Р-61.

### Р-66. Вердикт пары выравнивания — один `ok`; `suspect` и `critical` — сообщения сервиса (2026-11-02)

- **Было.** Модуль `voices` (`alignment.refusal`) отклонял озвучку не только при `ok=false`, но и когда сервис поднимал `suspect`
  или `critical`. Правило шло из CHARTER (требование 7) и попало в ТЗ этапа 10.
- **Что показала живая проверка.** Версия серии на dunhuatv.ru и версия канала VK различаются (выпадает начало около 127 с). Сервис
  сопоставил 79–82 % кадров, убрал расхождения, записал дорожки и вернул `ok=true` с `suspect`; модуль три из четырёх дорожек отклонил.
- **Решение владельца.** Всё, что конформ выдал рабочим, полностью здорово: он убирает несовпадения и отдаёт дорожку в такт референсу;
  `suspect` и `warnings` — просто сообщение о том, что он нашёл. Ошибка настоящая только когда кадры не совпадают совсем (два разных
  видео): тогда сервис возвращает `ok=false` и аудио не выдаёт.
- **Теперь.** Отклоняется результат с `ok=false` (причина — текст сервиса или `align_failed`), без результата в задаче и успех без файла.
  `suspect`, `warnings`, `critical` не отказ: сообщение пишется в журнал модуля и видно в очереди выравнивания. Интерфейс очереди
  считает пару принятой по одному `ok`. Коды причин `suspect`, `suspect_residual`, `critical` остаются в каталоге текстов ради
  уже записанных отказов.
- **Тесты.** `test_voices.py` (отказ только по `ok` и по отсутствию файла; `suspect` и `critical` кладутся, слова — в журнал),
  `test_contracts.py`, `web/src/lib/conform.test.ts`.


### Р-67. Круг ревью этапа 10: идентичность видео и части, участие варианта, команда синхронизации в БД (2026-11-02)

- **Было.** Независимое ревью (4/10) нашло на границах scan, downloads, voices и composition: строка с прежним ключом
  принимала другое видео и сохраняла скачанный файл (а downloads усыновлял файл прежнего видео под тем же именем); часть
  серии терялась в ключе озвучек; сезон 1 и «часть 1» назначала раскладка; отключение серии не пересчитывало план; выключение

  не был виден; рычаги и плееры расширялись правкой соседних узлов.
- **Решение.** (1) Адрес входит в идентичность скачанной строки: другое видео — строка версии, прежнее вытесняется планом,
  файл вытесняемого видео не усыновляется и убирается перед загрузкой нового. (2) Часть серии — часть ключа озвучки на всём

  пересчитывается. (5) Озвучка вне плана серии с известным референсом снимается в любом состоянии. (6) Поток даёт плеер
  (`stream` в контракте, граница высоты). (7) Команда видео-синхронизации — запись `scan_tasks`; scan, library, renaming
  возобновляют работу по `system.started`. (8) Провал пересчёта виден в «Выходе» и в источниках.
- **Решение владельца (ответы 2026-11-02).** Участие — свойство варианта «озвучка + источник + плеер» и действует на референс и на
  озвучки (рычаг `variant.allow` вместо `reference.allow`); «Выход» — сетка «озвучки × варианты»; рычаги рисуются по
  описаниям ядра; озвучку можно назвать (поле источника) и завести ей группу там, где она показана (миграция 0033); настройки
  следуют за озвучкой при смене группы.

### Р-68. Второй круг ревью этапа 10: задача привязана к своему видео, замена файла целым файлом, работа снимается исполнителем (2026-11-02)

- **Было.** Второе независимое ревью (5/10) нашло на тех же границах: ждущая задача скачивала прежнее видео после смены адреса
  строки, а повышение качества другого видео получало номер прежнего; прежний файл удалялся до получения нового; запрет варианта

  сквозного прибора допускал пустые пары.
- **Решение.** (1) Строка с задачей в очереди не меняет адрес на месте, идентификатор версии включает адрес видео, запись адреса не
  касается строки, которую уже качают. (2) Загрузка пишет под именем задачи рядом с файлом и встаёт на имя видео целым файлом; прежний
  файл заменяется после успеха, строки, державшие его, отпускают его в той же записи; усыновление не берёт файл, который оставит
  задача другой строки. (3) Владелец работы публикует `work.withdrawn`, исполнитель останавливается и убирает своё сам; приказ
  `downloads.fetch.cancel` снят. (4) Озвучка, шедшая из исключённого варианта, снимается на любом шаге, исключённые запасные убираются

  выключено побеждает, равные выборы — один, разные возвращаются уровню выше; из озвучек, ставших одной, остаётся строка с готовой

  уходящие строки. (8) Допустимые формы рычага — список в ядре (`LEVER_FORMS`), окно рисует их все. (9) Вердикт сквозного прибора —
  `verdicts.judge_alignment`. (10) На диске лежит то, что настроено в панели: загрузка, чьё видео вышло из плана, останавливается сама, целый
  файл серии, снятой настройкой, убирается, строка снова «не загружена»; статус плана `removed` — у строк отключённого сезона, снятого источника

  референс с дырой не сохраняется, ошибка «обрыв» повторяется по общему бюджету; озвучка принимается по методике track-muxer без этой проверки (сервис учитывает вырез как тишину). (13) Третий круг
