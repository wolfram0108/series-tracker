## 7. Хронические зависания воркера: ~190 WORKER TIMEOUT за полгода
(Первая версия этой находки ошибочно винила `max_requests=1000` —
опровергнута журналом systemd.) Журнал юнита wolfram-ts.service
(мастер pid 245): с декабря 2025 по июнь 2026 — около 190 событий
`[CRITICAL] WORKER TIMEOUT`. Воркер зависает намертво (все потоки
разом, SSE обрывается посреди строки), мастер ждёт `timeout = 120`
секунд, убивает его и пересоздаёт — с полным рестартом агентов и
переавторизацией qBittorrent; итоговое окно недоступности ~2 минуты.
Зависания идут сериями с интервалом ~1,5 часа, в том числе ночью без
какой-либо нагрузки (12–13 мая — вся ночь подряд): триггер внутренний
(агенты/фоновые циклы), а не HTTP-трафик. «Стабильность» прода — это
watchdog Gunicorn, полгода маскировавший хроническую болезнь.
Первопричину в старом коде не ищем (код пересоздаётся), но:
**Требования к новой системе:** (а) сохранить watchdog уровня процесса
(systemd Restart=always + healthcheck); (б) перезапуск без 2-минутного
окна — быстрый старт модулей, reconcile вместо «первоначальных
проверок»; (в) зависание одного модуля не должно замораживать весь
процесс — блокирующие операции только в executor'ах с таймаутами;
(г) на этапе 4 при переносе агентов выяснить, что в них тикает с
периодом ~1,5 часа — кандидат в первопричину, должен быть учтён.

## 24. SSE series_updated несёт неполный объект сериала
_update_and_broadcast шлёт голую строку таблицы series: без statuses

`s.statuses || s.state.split(...)` (app.js:66) — фронт готов принять
массив статусов, бэкенд его никогда не присылал.

## 25. Каскадные дубли broadcast при одном изменении

## 26. Ресьюмабельность scan_tasks — фиктивная

## 27. Скан без блокировок: ручной и автоматический могут пересечься

ждёт fetch всё это время). Автоскан-поток (_perform_full_scan)

с ручным сканом того же сериала нет, два скана могут идти параллельно
и наперегонки писать торренты/медиа-элементы.

## 30. Очередь загрузок: полный список в SSE каждые 5 секунд
DownloaderAgent._tick шлёт download_queue_update со ВСЕМИ активными
задачами каждые 5 с независимо от изменений + agent_heartbeat — вторая
половина SSE-шторма (к находкам 4/25). Прогресс в БД при этом пишется

## 31. Ошибочные загрузки ретраятся только перезапуском сервиса
requeue_stuck_downloads при старте переводит в pending задачи и
'downloading', и 'error'. В работающем процессе error-задачи не
ретраит никто, лимита попыток нет (attempts копится в никуда). При
следующем скане get_download_task_by_uid ищет только
pending/downloading → для того же uid создаётся ВТОРАЯ задача, старая
error-запись остаётся мусором до ручной очистки очереди.

## 32. Задачи, выпавшие из плана, зависают в pending навсегда
Добор задач JOIN'ится по plan_status ∈ in_plan_* — если элемент после
пересчёта плана выпал (replaced/redundant), его pending-задача больше
никогда не будет выбрана и не удаляется. Копится до ручного clear.

## 33. Задачи single_vk создаются и удаляются без выполнения
logic/task_creator.py при каждом скане создаёт renaming_tasks типа
'single_vk' (с old_path/new_path), но диспетчер RenamingAgent
(_process_task) обрабатывает только mass_torrent_reprocess и
mass_vk_reprocess — для single_vk нет ветки, задача помечается
in_progress и тут же удаляется как «успешно завершённая», не сделав
ничего. Реальное переименование одиночных файлов выполняет
mass_vk_reprocess при каждом скане. Побочный эффект: пока single_vk
задачи висят pending, сериал считается is_busy (блокируется карточка).

## 34. get_pending_renaming_task определён в Database ТРИЖДЫ

## 35. Автофильтр глав всегда бракует главу на 00:00:00
ChapterFilter._estimate_chapter_duration «оценивает длительность» по
времени НАЧАЛА главы (время конца недоступно), поэтому глава, начинающаяся
в 00:00:00, всегда получает «слишком короткая: 0сек» и бракуется. На
практике первая глава компиляции — почти всегда опенинг, так что
эвристика «угадывала» по ложной причине. Порт 1:1 (контракт UI —
согласовано в Р-16); пересмотр эвристик — отдельным решением, если
когда-нибудь понадобится.

## 36. Ошибка переобработки блокировала карточку навечно

## 41. Булевы колонки: SQLite 0/1 против true/false старого контракта
Обнаружено пользователем на стенде (этап 6): данные конструктора
перенеслись целиком, но переключатель «продолжить обработку» у всех
правил выглядел выключенным. Это не повреждение JSON — недоконтракт:
старый бэкенд (SQLAlchemy Boolean) отдавал true/false, новый (sqlite3
напрямую) — 0/1, а v-model чекбокса в Vue 3 сравнивает строго и не
считает 1 включённым. Затронуты все BOOLEAN-колонки, уходящие наружу:
auto_scan_enabled (series), continue_after_match (parser_rules),
is_ignored_by_user / is_available (media_items), is_active (torrents).
Фикс: Database.coerce_bools — владельцы таблиц приводят свои булевы
колонки на выдаче (catalog, rules, scan, torrents).

## 42. Детектор «разлогинены» Kinozal не узнавал форму со слешем
Обнаружено пользователем на стенде (этап 6): добавление сериала Kinozal
давало 400, в логе «ссылка download.php не найдена». Мониторинг
(категоризированные логи новой системы, group=sources) сразу показал
причину: trackerauth отдавал sources гостевую страницу без релогина.
KinozalProvider.is_logged_out искал точную подстроку
'action="takelogin.php"', а реальная форма входа — action="/takelogin.php"
(со слешем). Детектор возвращал False для гостя → релогин не
запускался → парсер не находил ссылку. Старая система проблемы не имела
по другой причине: она логинилась при КАЖДОМ создании сессии (кэш
только в памяти), без детектора. Новая — лениво (персистентные куки,
переживает рестарт), поэтому детектор обязан быть точным. Фикс: regex
action=['"]?/?takelogin\.php (устойчив к слешу и кавычкам); на
залогиненных страницах формы нет вовсе. Регрессия — в test_trackerauth.

## 43. Торрент в qBit-state error/missingFiles показывался как «загрузка»
Обнаружено пользователем на стенде (этап 6): добавил торрент с неверным
путём, qBittorrent держит раздачу в state="error", но карточка показывала
«Загрузка». Причина — свёртка torrents._contribute: qBit-состояния
ошибок не входили в _NOT_DOWNLOADING, прогресс<100 → флаг downloading.
Тот же дефект был в старой системе (status_manager.sync_torrent_statuses:
status not in ['pausedUP','pausedDL','uploading']) — унаследован, не

## 46. Многопоточная загрузка VK (hls+-N) + мониторинг постобработки

## 48. Deadlock постобработки: ffmpeg/yt-dlp виснут на непрочитанном stderr
Обнаружено пользователем: загрузка застряла «обработка 100%, ETA

тесте не воспроизводилось (мало stderr) — снова урок golden-sample на
РЕАЛЬНЫХ данных. Фикс: _drain_stderr — параллельное вычитывание stderr
(копим хвост для текста ошибки). Проверено на реальном файле: remux
идёт без зависаний, за 30с вычитано 2732 строки stderr, out_time растёт.

## 52. Прогресс remux всегда 100%: заниженная длительность из ffprobe TS

контентных путях:

| Путь | Ответ |
|---|---|
| `/forum/index.php` | 200 |
| `/forum/viewtopic.php?t=…` | 403 challenge |
| `/forum/viewforum.php?f=…` | 403 challenge |
| `/forum/tracker.php` | 403 challenge |
| `/forum/login.php` | 403 challenge |

| Способ | Результат |
|---|---|
| requests с браузерным User-Agent | 403, челлендж |
| cloudscraper (наш путь для astar) | 403, челлендж |
| curl_cffi, подмена TLS-отпечатка (JA3) под Chrome/Firefox/Safari | 403, челлендж |

защита не опознаёт как автоматизированный. Ложная версия «нас режут по

сайт без проверок.

Второй слой находки: форма входа rutracker теперь содержит капчу
(`cap_sid`, `cap_code_<хэш>`) — автоматический релогин невозможен в
принципе. Спасло то, что `bb_session` в БД (от 13.06) остался жив: он
живёт месяцами, а падения были не из-за протухшей сессии.

Класс бага: доставка страницы имеет ТРИ состояния, а код знал два —
«сессия жива» и «сессия протухла». Третье, «клиент не пущен защитой»,
маскировалось под обычную HTTP-ошибку, поэтому перебор зеркал молотил
впустую, а `is_logged_out` (справедливо) не видел причины для релогина.

Фикс (структурный, в trackerauth — владельце доставки, Р-1):
- `cf_challenge.py` — прохождение челленджа настоящим браузером;
  признак успеха детерминированный (появление куки `cf_clearance`), а не
  подстрока «Один момент…»/«Just a moment…», зависящая от языка;
- `RutrackerProvider.is_challenged` — детект по заголовку
  `cf-mitigated: challenge`; `challenge_url` — челлендж для `dl.php`
  проходится на странице темы (файл в браузере не открыть);
- `on_fetch` проверяет челлендж ПЕРВЫМ (пока защита не пустила, тело
  ответа — её заглушка, судить по нему о своей сессии нельзя), проходит
  его и повторяет исходный запрос; rate-limit `CHALLENGE_MIN_INTERVAL`
  не даёт зациклиться на запуске браузера;
- `cf_clearance` действителен только в паре с UA, которым получен, —
  поэтому UA стал частью состояния сессии: колонка `tracker_sessions.
  user_agent` (миграция 0007), восстанавливается вместе с куками и
  перекрывает провайдерский UA в запросе;
- релогин больше не сбрасывает клирэнс (`_login` его сохраняет): клирэнс
  про клиента, а не про учётку, иначе каждый вход тянул бы лишний прогон
  браузера;
- бюджеты времени согласованы: прохождение челленджа (до 45 с) должно
  укладываться в ожидание потребителя, поэтому `sources` ждёт
  `trackerauth.fetch` 150 с вместо 60/90 — иначе запрос отваливался бы
  по шине посреди успешного прохождения.

Проверено на живой системе: скан сериала 30 → челлендж пройден за 11 с →
`.torrent` скачан → раздача добавлена в qBittorrent и качается
(9.3 ГБ, 8.2 МБ/с). Новых ошибок в логе нет.

Ограничение, которое нужно помнить: если `bb_session` всё же умрёт,
автоматический вход упрётся в капчу — потребуется разовый ручной вход.
Сообщение об этом сделано явным (`RutrackerProvider.login` отличает
капчу от неверного пароля).

## 66. Антибот-челлендж объявлялся поштучно в провайдере (ИСПРАВЛЕНО)

Kinozal включил Cloudflare managed challenge на контентных страницах

Второй дефект того же класса: клирэнс действителен только в паре с UA,
которым получен, но подстановка «прогретого» UA жила в общей обёртке

разворачивала его прямо на странице входа.

Класс бага: инвариант транспорта применяется на одном пути и объявляется
поштучно потребителем. Всё, что ходит мимо общей обёртки или не объявило
способность, выпадает молча.

Фикс (структурный, в trackerauth):

| Было | Стало |
|---|---|
| `is_challenged` в провайдере | `cf_challenge.is_challenge` — один детектор по заголовку Cloudflare |
| челлендж проверялся в `on_fetch` | `cf_challenge.arm(session)` — запрос с заглушкой поднимает `ChallengeSeen` вместо ответа |
| прохождение и повтор — в `on_fetch` | `_with_clearance` — одна точка, общая для запроса и логина |
| UA подставлялся в обёртке запроса | UA — свойство сессии; провайдер объявляет его данными (`user_agent`) |

Заглушка защиты больше не может доехать до кода как ответ сайта — ни по
одному пути, включая логин провайдера.

Тесты переведены на подмену транспорта (HTTP-адаптер) вместо
`Session.request`: хуки на ответ и склейка заголовков в тесте настоящие,
иначе проверка не видит того, что видит рабочий код.

Проверено на живой системе: kinozal — челлендж пройден за 13 с, клирэнс
сохранён, повторный скан идёт без браузера (0.3 с); rutracker — релогин
прошёл, найдена новая раздача, задача конвейера создана. Все сериалы,
падавшие на разборе страницы, сканируются без ошибок.

2026-09-17. Симптом: в БД путь

мимо единого нормализатора.

Фикс (структурный, одно правило на обе стороны):

| Было | Стало |
|---|---|
| правило внутри `rules.formatter` | `core/fsnames.py`: `sanitize_name` / `sanitize_path`; форматтер использует его же, вывод имён файлов не изменился |

которые такие имена не открывают. Точки в конце компонента не режутся (как
и прежде в форматтере). Русское название не нормализуется: оно только для
показа.

(каретка, пробелы, программные значения); границы catalog / library /
settings — в тестах соответствующих API.

## 69. Вход на трекер не был привязан к учётным данным (ИСПРАВЛЕНО)

2026-10-12. Симптом: после смены учётной записи Кинозала в настройках
скачивание `.torrent` продолжало падать с «достигнут суточный лимит
скачиваний», хотя у новой записи лимит не тронут.

Причина: сессия жила в двух слоях, а отменялась в одном.

(`tracker_sessions`) куки оставались, и `_get_session` их оттуда
восстанавливал. Релогин запускается только по признаку протухания, а
прежняя сессия была жива: куки валидны, пользователь авторизован,
исчерпан лишь его суточный лимит. Протухания нет — значит входа нет,
значит новая учётная запись не применялась никогда.

Состояние на момент разбора: кука `uid` одинакова на обоих зеркалах
(`20430818`), последний вход — 24 августа и 3 сентября, страница трекера
под этой сессией отдавала «Выход» — система работала под прежним
аккаунтом.

а инвалидация написана для одного — персистентный слой воскрешает
отменённое состояние. Нарушение правила «шина — сигнал, БД — истина»:
сброшен сигнал, не тронута истина.

Фикс (структурный: применимость решается отпечатком, а не явным сбросом):

| Было | Стало |
|---|---|
| сброс сессий при смене учётки только в памяти | `tracker_sessions.account_fingerprint` (миграция 0009): куки авторизации выдаются только под те же учётные данные |
| ключ кэша сессий `(service, domain)` | `(service, domain, отпечаток)` — сессия прежней учётки по новому ключу не находится |
| смена пароля той же записи не замечалась | отпечаток считается от логина И пароля (пароль входит хешем) |
| логин сохранялся как введён | `upsert_credentials` срезает пробелы по краям |
| причина в журнале не видна | «сессия получена под другой учётной записью — нужен вход» и «логин под учётной записью <логин>» |

Клирэнс антибот-защиты и UA от привязки свободны: они про клиента, а не
про учётку (находка 65), поэтому смена учётной записи не тянет за собой
прогон браузера.

Два состояния различаются строго: NULL — «неизвестно, под какой учёткой
получена» (запись старше привязки), и это НЕ «получена под другой».
Отбрасываются куки только при явном несовпадении отпечатков. Иначе
терялась бы рабочая сессия там, где автоматический вход невозможен:
форма входа RuTracker содержит капчу (находка 65), и живая `bb_session` —
единственный способ работы с трекером.

Отмена прежнего входа при смене учётных данных выполняется явно и в
обоих слоях: `credentials.set` чистит кэш сессий в памяти И выбрасывает
куки авторизации из БД (`drop_account_cookies`), сохраняя клирэнс и UA.
Отпечаток — страховка от рассинхрона, а не замена инвалидации.

Проверка на живой системе: запрос к `kinozal.guru` → «получена под другой
учётной записью» → вход под записью из настроек → `userdetails.php?id=
19426853` вместо прежнего `20430818`; сквозной запрос `.torrent` по ссылке
`dl.kinozal.me` → вход на `kinozal.me` под той же записью → файл 70 590
байт, лимита нет. Тесты (`tests/test_trackerauth.py`): отпечаток следует
за логином и паролем, чужая сессия не применяется при сохранённом
клирэнсе, своя переживает рестарт без лишнего входа, пробелы в логине
срезаются.

## 70. Файлы проигравших разрешений оставались на диске (ИСПРАВЛЕНО)

`replaced` — только пометка плана; файл никто не удалял (в контракте VU9:
«файл остаётся до замены», замена не написана). Вход планировщика — строки со
статусом `candidate`, то есть только вернувшиеся из последнего скана, поэтому
прежняя строка эпизода выпадала из пересчёта и оставалась `in_plan_single` —
два «победителя» в слоте. Следствие в медиатеке (Plex/Jellyfin): 2–3 версии
одной серии; счётчик «скачано» завышен. Исправление — Р-37 (план по всем
строкам, `superseded_by`, `_retire_superseded`, `upgrade_unique_id`).

## 71. Объявленный Vibix-поток принимался без проверки (ИСПРАВЛЕНО)

Плейлист Vibix содержит потоки, манифест которых CDN может не отдавать (400).
Кандидат выигрывал эпизод по объявленному разрешению; при ошибке разрешения
потока загрузчик отдавал yt-dlp страницу серии, и тот сообщал ошибку другого
плеера (закрытый VK). Нарушение требований «источник выбирается по факту доступности» и «недоступный
источник не уходит в загрузку» (находка 119) для Vibix. Исправление — Р-37 (проверка манифеста, `StreamUnavailable`,
явная ошибка задачи).

## 72. Загрузчик передавал ffmpeg только Referer (ИСПРАВЛЕНО)

Провайдер возвращал `headers` потока, но `ytdlp._download_direct_ffmpeg` брал из
них только `Referer`. Для VK через CDN VideoHub ссылка подписана на
User-Agent выдавшего её запроса; `ffmpeg` с собственным агентом получал 400.
Теперь `User-Agent` уходит в `-user_agent`, остальные заголовки — в `-headers`
(`ytdlp._headers_args`). Р-38.

## 73. Метка ступени лестницы VK не равна разрешению (УЧТЕНО)

У агрегатора CDN VideoHub ступень `mpeg4kUrl` оказалась кадром 2560×1440.
Метки выше `FullHd` не переводятся в высоту таблицей: поток измеряется
`ffprobe`, а не измеренная ступень не выбирается. Р-38.

## 74. Загрузка потока без переподключений и без проверки полноты (ИСПРАВЛЕНО)

`ytdlp._download_direct_ffmpeg` запускал `ffmpeg -i <url> -c copy` без опций
переподключения. CDN Kodik замирает при открытии и обрывает поток на середине:
загрузка падала с `Connection timed out` и `Input/output error`, а повторы
попадали на тот же сбой. Обратное: `ffmpeg` завершается с кодом 0 и на
оборванном HLS, поэтому обрубок принимался за серию. Методика сервиса
выравнивания: `-reconnect 1 -reconnect_streamed 1 -reconnect_on_network_error 1
-reconnect_delay_max 30` перед `-i` и проверка длительности результата против
объявленной потоком (порог 0,85). Теперь так же: опции только для сетевых
потоков, сторож простоя (нет прогресса 180 с) и предел времени, повторная проба
длительности, обрыв — временная ошибка. Касается всех прямых загрузок
(референсы и озвучки). Р-41.

## 75. Сервис выравнивания оставляет пустой `_tmp` рядом с референсом (УЧТЕНО)

Рабочая область запуска сервиса создаётся каталогом `_tmp` рядом с данными, а
удаляется только вложенный каталог запуска: пустой `_tmp` остаётся в каталоге
референса, то есть в медиатеке. Модуль `voices` убирает пустой `_tmp` после
расстановки дорожек, пока у сериала не идёт ни одна задача (при идущей задаче
каталог нужен сервису; замок сериала не даёт поставить новую в этот момент).
Непустой `_tmp` не трогается. Р-41.

## 76. Смена имени файла серии не объявлялась (ИСПРАВЛЕНО)

`downloads.item.set_filename` только писал `final_filename` в БД; события не было.
Модуль с файлами рядом с видео (дорожки озвучек) не узнавал о переименовании и
остался бы с дорожками под старым именем до следующего скана. Владелец имени
теперь объявляет смену событием `downloads.item.renamed`; перенос библиотеки
объявляется `library.relocation.finished`. Р-42.

## 77. Итог задачи выравнивания, пришедший раньше записи её номера (ИСПРАВЛЕНО)

Сервис может завершить задачу (например, пропустив готовые дорожки) раньше, чем модуль записал
номер задачи у озвучек: событие не находило ни одной записи и пропадало, озвучки оставались «на
выравнивании» навсегда. Номер задачи теперь записывается всем озвучкам серии одним запросом, итог,
пришедший раньше записи, запоминается и применяется после неё. Р-45.

## 78. Запоздалое завершение загрузки превращало ждущую озвучку в «скачана» (ИСПРАВЛЕНО)

Обработчик завершения загрузки не проверял состояние озвучки: повторное или запоздалое событие о
ключе, чья озвучка снова ждала загрузки, ставило «скачана» без файла. Событие принимается только для
озвучки в загрузке; перед постановкой серии проверяется, что файлы скачанных озвучек на месте. Р-45.

## 79. Разбор страницы сайта без каталога озвучек (ИСПРАВЛЕНО)

После каждого скана серии web-источника модуль озвучек заново разбирал страницу сайта, чтобы узнать,
что озвучек у него нет (у ruchime — чтение страницы и проба плееров). Провайдер объявляет
`has_voice_catalog`, `sources.provider.info` отвечает без сети, разбор выполняется только для
провайдеров с каталогом. Р-45.


## 80. Перенос дорожки не был атомарным относительно БД (ИСПРАВЛЕНО)

Файл перемещался раньше, чем строка узнавала новый путь; падение между ними оставляло дорожку без
владельца. Намерение (`move_from`, `sidecar_path`) записывается до перемещения, завершение и сверка при
старте исходят из него. Р-46.

## 81. Отказы удаления файлов проходили молча (ИСПРАВЛЕНО)

Ошибка удаления файла или каталога глоталась, строка при этом считалась очищенной. Удаление идёт через
`_discard`, отказ пишется в журнал `voice_cleanup` и повторяется. Р-46.

## 82. Потерянный ответ на постановку в сервис порождал дубль или вечное ожидание (ИСПРАВЛЕНО)

При обрыве между отправкой и ответом задача либо отправлялась повторно, либо строки ждали номер,
которого нет. Постановка идёт по ключу из метки задачи, итог неизвестности разрешается запросом
`conform.job.find`. Р-46.

## 83. Длина дорожки не сверяется с видео (РЕШЕНИЕ)

Выход выравнивания — эталон синхронизации; расхождение длины возможно только из-за неверного замера
или дефекта контейнера референса, то есть проверка давала бы ложные отказы. Несогласованные входы
(разные видео под одним номером серии из-за ошибки CDN или релизёра) сервис возвращает результатом пары
`ok=false` с текстом ошибки, задача при этом завершается `done`; озвучка становится `rejected`. Р-46.

## 84. Интерфейс мог расходиться с БД (ИСПРАВЛЕНО)

Создание запланированных строк, исключение из плана и удаление сериала не сообщались; пакеты не имели
порядка; открытый экран зависел от HTTP-загрузки, которая могла прийти позже события. Все записи
объявляются, пакеты несут `rev`, при подключении клиента приходит снимок. Тесты сверяют картину из
событий с картиной БД. Р-46.

## 85. Номер серии из другого сезона затирал серию в каталоге CVH (ИСПРАВЛЕНО отказом)

Каталог озвучки собирался словарём «номер серии → видео»; серия второго сезона с тем же номером молча
заменяла серию первого. Каталог с такими совпадениями отклоняется с причиной. Р-46.

## 86. Настройки, пути и ключи озвучек зависели от состояния на момент чтения (ИСПРАВЛЕНО)

Неверное значение настройки молча заменялось умолчанием; пути брались из текущих настроек и карты
путей сервиса; смена правил делала размещённую озвучку «новой». Настройки разбираются типизированно с
названием проблемы, пути берутся из строк, ключ голоса сохраняется. Р-46.

## 87. Причины отказов — русские предложения в ядре (ИСПРАВЛЕНО)

Модуль формировал готовые русские строки, которые интерфейс показывал как есть. Причины — коды с
фактами, слова в каталоге интерфейса; число русских литералов в экранах ограничено тестом. Р-46.

## 88. Знание об одной политике было размазано по слоям (ИСПРАВЛЕНО)

Переходы статусов проверялись в оркестраторе, SQL, восстановлении и компоненте интерфейса; устройство
результата сервиса выравнивания (папки, имена файлов) и форма выдачи (дорожка рядом с видео) были вшиты в
размещение, перенос, удаление и структуру записи. Переходы описаны таблицей, чтение результата — адаптером,
форма выдачи — стратегией; колонка названа по назначению. Р-47.

## 89. Контракты между модулями описывались несколькими независимыми текстами (ИСПРАВЛЕНО)

Источники, события, снимок, раскладка и итог задачи выравнивания передавались словарями, состояния —
произвольными строками, а интерфейс объявлял собственные типы и приводил их. Описание сделано один раз
(`core/contracts`), проверяется у производителя и потребителя, типы интерфейса генерируются из схемы API;
тесты сверяют перечисления и поля моделей с сгенерированными типами и каталогом текстов. Р-47.

## 90. Итог задачи, пришедший во время записи её номера, мог остаться без применения (ИСПРАВЛЕНО)

Обработчик итога проверял, есть ли у озвучек номер задачи, а потом запоминал итог; запись номера и
проверка запомненного итога шли между ними. При такой очерёдности итог оставался в памяти, озвучки — в
выравнивании до перезапуска. Проверка-и-запись итога и запись-номера-и-проверка итога идут под одной
блокировкой; тест воспроизводит перекрытие и падает без блокировки. Без блокировки тест
«итог раньше номера» падает и сам (1 из 18 прогонов в 6 параллельных потоков), с блокировкой — 0 из 24. Р-47.

## 91. Короткие запросы к внешним программам ждали без предела (ИСПРАВЛЕНО)

Запрос длительности у `yt-dlp` (`downloads`) ждал ответа без срока и не останавливал процесс при отмене;
запрос глав (`slicing`) убивал процесс по сроку, но не дожидался его завершения и не останавливал при
отмене. Оба идут через `core.proc.run_capture`: по сроку и при отмене процесс убит и подобран. Долгие
потоковые процессы загрузки (прямая загрузка `ffmpeg`, `yt-dlp`, `remux`) читают вывод через один помощник
`_next_line`: молчание дольше `STALL_TIMEOUT_S` останавливает процесс, ошибка помечена как временная и
повторяется (у `yt-dlp` и `remux` общего срока нет — большие файлы идут долго, пока выводят прогресс).
Процесс убивается и при отмене. Р-46.

## 92. Отложенное удаление шло по имени и уничтожало новую работу под тем же именем (ИСПРАВЛЕНО)

Журнал очистки повторял удаление пути без проверки, чем занят путь теперь. Если после отказа удаления
озвучка начала заново и получила то же имя временного файла или дорожки, очередной проход уничтожал
новый файл. Запись журнала, чей путь (или каталог над ним) снова числится за живой озвучкой, снимается
без удаления. Р-46.

## 93. Тест корня «/» зависел от сборки фронтенда в рабочем каталоге (ИСПРАВЛЕНО)

`test_security_headers_present` запрашивал «/», а шлюз без каталога сборки по умолчанию (`web/dist` от
рабочего каталога) отдаёт запасную страницу, которой в тесте нет: на чистом снимке тест падал.
Фикстура шлюза получает собственную заглушку сборки; серверные тесты от `web/dist` не зависят.

## 94. Причины провайдеров — русские предложения серверной части (ИСПРАВЛЕНО)

Отчёт о плеерах, пометки пропусков серий и сообщения исключений провайдеров (`dunhuatv`, `cdnvideohub`,
`kodik`, `ruchime`, `players`, `vibix`) формировались готовыми фразами, которые интерфейс выводил как есть:
тот же класс, что находка 87, вне озвучек. Все производители строят причину через `core.reasons.reason`,
интерфейс читает её одной функцией `reasonText`; прежние записи отчётов (обычный текст) показываются как
внешний текст. Р-48.

## 95. Файловые вызовы вне озвучек ждали без предела (ИСПРАВЛЕНО)

Модули `slicing`, `downloads`, `renaming`, `library`, `torrents`, `sources` уводили вызовы файловой системы в
общий пул `asyncio.to_thread` без срока, а `library` и загрузчик (`ytdlp.py`) вызывали часть из них прямо в
цикле событий. Все такие вызовы идут через `core.storage.call` с пределом ожидания по весу вызова
(`DEFAULT_TIMEOUT_S`, `REMOVE_TIMEOUT_S`, `MOVE_TIMEOUT_S`); зависшее хранилище даёт `TimeoutError`
(подкласс `OSError`, прежние обработчики его ловят), а не вечное ожидание. Охранный тест
`tests/test_storage_calls.py` запрещает `asyncio.to_thread` в модулях, кроме сетевых запросов
`trackerauth` и диагностики `gateway`. Р-46.

## 96. Событие описывало намерение вызывающего кода, а не записанное изменение (ИСПРАВЛЕНО)

После неудачного размещения дорожки модуль сообщал «ошибка», затем «размещена»: событие строилось из того, что
вызывающий код собирался записать, а результат записи игнорировался. Теперь каждое событие строится из
сохранённой записи (`_announce`: версия берётся до чтения, статус и причина — из строки; «устарела»,
«перенесена», «удалена» объявляются только если строка это подтверждает). Результат `_finish_move` останавливает
размещение и следование. Р-50.

## 97. Успех без файла и сбой одной озвучки останавливали обработку пакета (ИСПРАВЛЕНО)

Модель допускает `{ok: true, out_path: null}`, обработчик вызывал `os.path.isfile(None)`, и исключение
оставляло озвучки в «выравнивании». Адаптер выдаёт отказ `output_missing` на успех без файла; результат каждой
озвучки обрабатывается отдельно, неразобранный результат завершает только её отказом `result_unreadable`. Р-50.

## 98. Перезапуск не возобновлял начатый перенос размещённой дорожки (ИСПРАВЛЕНО)

Серии для возобновления выбирались по основному статусу озвучек (`ready`, `aligned`); строка `placed` с начатым,
но не завершённым переносом (`move_from`) оставалась до постороннего события. Выборка
`series_with_open_work` берёт и серии с любой начатой, не завершённой операцией. Р-50.

## 99. Защита от повторяющихся номеров серий смотрела на группу уже, чем сопоставление (ИСПРАВЛЕНО)

Сезон отбрасывается для каталога целиком, а проверка группировала серии по (студия, тип, номер): номер,
общий для сезонов разных озвучек, проходил. Проверка идёт по номеру серии в пределах всего плейлиста. Р-50.

## 100. Потерянный HTTP-ответ на постановку считался отказом (ИСПРАВЛЕНО)

`conform.submit` отвечал «не отправлено, повторить» на любую ошибку HTTP, включая обрыв чтения после того, как
демон принял задачу; `voices` сбрасывал ключ и отправлял другую задачу, а поиск по ключу не вызывался. Исходов
четыре: принято (`job_id`), отклонено (`rejected`), не отправлено (`unavailable`: нет настройки, демон не
поднят, сбой до отправки запроса) и исход неизвестен (`uncertain`: любая другая ошибка HTTP, включая ответ 5xx).
При неизвестном исходе ключ сохраняется и вопрос задаётся сервису. Собственные сообщения `conform` — коды.
Сквозной тест `tests/test_voices.py` (настоящий `conform` над сценарным демоном) падает на прежней классификации. Р-50.

## 101. Каталог результата восстанавливался по косвенному признаку (ИСПРАВЛЕНО)

Каталог, куда задача просила положить дорожки, считался по первой озвучке пакета, а путь результата каждой
озвучки — по её собственному `temp_path`; при смене корня между загрузками дорожка искалась не там. Каталог
сохраняется при постановке (`out_dir`, миграция 0021) и служит единственным местом поиска результата; для строк,
поставленных до миграции, он выводится как раньше. Р-50.

## 102. Порядок пакетов держался на системных часах (ИСПРАВЛЕНО)

Версия пакета `rev` была счётчиком в памяти, поднятым до системного времени; после перезапуска при отведённых
назад часах пакеты нового запуска оказывались «старее» тех, что интерфейс уже видел, и он отвергал и снимок, и
изменения. Порядок задают номер запуска модуля `epoch` (хранится в БД, растёт при каждом запуске, миграция 0022)
и счётчик `rev` внутри запуска; часы в порядке не участвуют. Интерфейс сравнивает пары. Р-50.

## 103. Конец ожидания принимался за конец файлового действия (ИСПРАВЛЕНО)

Вызов хранилища, не ответивший за срок, продолжал работать в потоке, а путь считался свободным: запись журнала
очистки снималась проверкой «имя занято живой озвучкой», затем поздний поток удалял уже новый файл. Вызов,
который меняет файлы, объявляет, чем владеет (`core.storage.call(..., owns=...)`); владение кончается, когда
возвращается поток, а не когда кончилось ожидание. Пока путь (или путь внутри него, или родственный артефакт)
занят, изменяющий вызов на нём отклоняется (`StorageBusy`), озвучки не начинают на нём загрузку, постановку и
размещение и просят сообщить об освобождении (`storage.when_free`), проход очистки не трогает запись, загрузчик
не начинает загрузку на это имя. Носители: озвучки, `slicing`, `renaming`, `library`, `downloads`, `sources`. Р-50.
Сравнение времени изменения файла с часами сервера, вводившееся как вторая защита, убрано в находке 105.

## 104. Модуль озвучек знал устройство папок демона и неиспользуемые операции выдачи (ИСПРАВЛЕНО)

`voices` держал имена папок демона (`_aligned`, `_cache`, `_tmp`) и выводил по ним путь дорожки; контракт `Output`
содержал операции `deliver` и `follow`, которые оркестратор не вызывает (всё делает `settle` по записанному
намерению). Раскладка папок известна только мосту: `voices` спрашивает `conform.workspace`; контракт `Output`
сужен до четырёх операций, которые используются. Выдача, объединяющая видео и все дорожки в контейнер,
требует контракта серии; этап для неё не начат. Р-50.

## 105. Пропуск действия неотличим от его выполнения (ИСПРАВЛЕНО)

Удаление дорожки, чьё время изменения было позже запроса (расхождение часов хранилища и сервера, достаточное для
срабатывания), возвращало управление без удаления; журнал очистки не получал записи, строка озвучки сбрасывалась,
устаревшая дорожка оставалась рядом с видео. Сравнение с часами убрано: от записи самого приложения имя охраняет
владение (находка 103), от отложенной очистки — запись живой озвучки и папка, в которую пишет идущая задача.
Удаление подтверждается освободившимся именем, а не отсутствием ошибки, и кончается одним из двух: имя свободно
или оно в журнале, который доводит до конца исполнитель восстановления. Тот же класс в `downloads` и `slicing`: пять мест
молча проглатывали отказ удаления ненужного файла; теперь это одно место — `core.storage.remove_file`/`discard`
(предупреждение с путём, результат), охранный тест ищет молчаливое удаление по коду. Р-51.

## 106. Проверка занятости пути вместо владения им (ИСПРАВЛЕНО)

Загрузчик проверял, не занят ли путь, и затем несколько раз ждал (длина потока, запуск программы); операция
хранилища, начавшаяся между проверкой и записью, делила каталог с идущей записью дочернего процесса. Владение
берётся одним шагом (`core.storage.hold`, проверка и захват без ожидания между ними) и длится, пока жив последний
пишущий под ним: поток вызова и программа, запущенная через `core.proc.spawn` внутри владения, прикреплены к нему,
поэтому владение кончается после записи, а не после ожидания. Вызовы того же владельца собственные и им не
отклоняются. Носители: `downloads` (прямая загрузка, `yt-dlp`, ремукс), `slicing` (нарезка). Программы запускаются
только через `core.proc` (проверяет тест). Р-51.

## 107. Исход отправки определялся типом исключения, а не фазой (ИСПРАВЛЕНО)

Общий перехват ошибок значений охватывал и подготовку путей, и разбор ответа на уже отправленный запрос:
повреждённый JSON ответа превращался в окончательный отказ, хотя демон мог принять задачу. Клиент отвечает
фазой: `DaemonRefused` (отказ), `NotDelivered` (запрос не мог подействовать, в том числе «повторите позже»),
`Unconfirmed` (запрос мог дойти, а ответу верить нельзя: обрыв чтения, ответ сервера 5xx, не JSON, нет номера
задачи). Подготовка путей отделена от отправки. Ответ моста — модель `SubmitReply` с четырьмя исходами; всё,
что не является ясным ответом, `voices` читает как неопределённый исход. Те же правила — для `job.find`
(нечитаемый список задач — «спросить нельзя») и `job.get` (демон, у которого не спросили, — не «задача исчезла»).
Р-51.

## 108. Восстановление не имело своего счёта попыток (ИСПРАВЛЕНО)

Сохранённое незавершённое действие (задача, отправленная без ответа; задача с неизвестным итогом; запись журнала
очистки; проход по серии) продолжалось только по постороннему событию: после неудачного вопроса к сервису
следующего прохода не назначалось. Каждое такое обязательство зарегистрировано в исполнителе восстановления
(`modules/voices/recovery.py`) с собственным счётом: пауза удваивается до потолка, `conform.daemon.up` ускоряет
следующую попытку, после заданного числа неудач владелец получает сообщение (ошибка в журнале), попытки идут
дальше с наибольшей паузой. Отправленная озвучка без номера задачи показывается подсказкой `awaiting_answer`.
Р-51.

## 109. Порядок обновлений реплики после удаления записей (ИСПРАВЛЕНО)

Интерфейс хранил версии отдельных озвучек; пустой снимок удалял отметки отсутствующих записей, поэтому пакет
существования, запоздавший после удаления и более нового пустого снимка, возвращал удалённую озвучку (так же —
пакет прежнего запуска после снимка нового). Хранилище держит границу последнего принятого полного снимка и
отвергает пакеты и снимки не новее её; отметки отдельных записей после этого безопасно забываются. Р-51.

## 110. Ресурсы задачи использовались повторно до подтверждённого конца прежнего владельца (ИСПРАВЛЕНО)

После замены референса неподтверждённая отмена оставляла прежнюю задачу работающей, а новая получала те же имена
входов и ту же папку результата: старая задача дописывала файлы, и итог новой задачи читал её байты. Строка
сбрасывалась, сведения о прежнем владельце файлов терялись. Каждая постановка пишет в папки своего поколения
(`<результат>/<ключ>`, `<кэш>/<ключ>`; ключ хранится со строкой), поэтому файлы прежней задачи недостижимы для
итога новой. Задача и отправка без ответа, которых ждала сбрасываемая строка, записываются в журнал очистки вместе
с папкой (`voice_cleanup.scope`, миграция 0023) в той же транзакции, что и сброс; запись кончается только
подтверждённой остановкой, после чего чистится папка. Носители: замена референса, серия вне плана (задача раньше не
отменялась), удаление сериала. Р-52.

## 111. Ссылка на имя принималась за передачу ресурса новому владельцу (ИСПРАВЛЕНО)

Запись журнала очистки создавалась до того, как строка отпускала указатель; исполнитель восстановления видел имя
в строке, считал его принадлежащим новой озвучке и завершал запись, потом строка отпускала указатель: файл
оставался без записи. Порядок «удалить, при неудаче записать» заменён: указатели строки, её задача и отправка без
ответа попадают в журнал в той же транзакции, что и сброс строки, удаление эпизода или серии и завершение
эпизода (`reset`, `drop_episode`, `settle_episode`, `delete_for_series`); удаление выполняется только из
журнала. Имя, найденное в строке после этого, принадлежит новому владельцу. Р-52.

## 112. Недостоверный ответ приравнивался к достоверному отсутствию (ИСПРАВЛЕНО)

Успешное чтение задачи с телом `null` превращалось в «задача исчезла», и озвучки уходили на повторную постановку.
Клиент проверяет форму успешного ответа (объект с номером искомой задачи, список объектов с номерами); отсутствие
подтверждается только `404`. Р-52.

## 113. Разрыв передачи обязательства при восстановлении номера задачи (ИСПРАВЛЕНО)

Восстановление номера по ключу завершалось, а обязательство узнать итог задачи не создавалось: задача, завершившаяся
во время остановки, не читалась. Номер, найденный по ключу, сразу передаётся обязательству `job:<номер>`. Р-52.

## 114. Сбой вычисления паузы кончал обязательство (ИСПРАВЛЕНО)

После 1024 неудач возведение в степень переполняло вещественное число, исключение выходило из исполнителя, и
обязательство удалялось. Степень ограничена; пауза, которую не удалось вычислить, заменяется запасной, и ни
ошибка планировщика, ни ошибка ожидания не означают, что работа выполнена. Р-52.

## 115. Очистка родительского каталога не учитывала владение незавершённой задачи (ИСПРАВЛЕНО)

Проверка допустимости удаления смотрела только на живые строки озвучек и только на потомков папки идущей задачи;
запись журнала о задаче с папкой (`voice_cleanup.scope`) в проверку не входила, а папка выше (серии, эпизода) не
считалась пересекающейся. После удаления сериала или завершения нового поколения очистка снимала дерево вместе с
файлами работающей задачи. Единая проверка (`_contested`) учитывает папки идущих задач живых строк и записи журнала о
задачах и отправках, не подтверждённых остановленными, в обе стороны: само место, вложенное и вышестоящее. Удаление
ждёт; остановка задачи будит ожидающие записи. Носители: `_clear` (файлы и деревья), очистка эпизода и серии,
выход эпизода из плана. Р-53.

## 116. Завершение записи журнала шло по имени без идентичности обязательства (ИСПРАВЛЕНО)

Проход очистки, приостановленный между удалением файла и снятием записи, снимал запись по имени; если за это время
новый владелец передал то же имя журналу, его запись пропадала. Запись несёт версию (`voice_cleanup.version`,
миграция 0024), повторная передача поднимает её; запись снимается только в прочитанной версии (`cleanup_done(путь,
версия)`); неудачная попытка версию не меняет (`note_cleanup_error`). Все места завершения (удаление, имя занято
новой озвучкой, остановка задачи) идут через одну функцию. Р-53.

## 117. Отсутствие задачи в момент поиска принималось за конец ещё действующей отправки (ИСПРАВЛЕНО)

Отправка, запрос которой ещё в пути, при удалении сериала получала запись журнала; поиск по ключу честно отвечал
«задачи сейчас нет», запись и папка снимались, потом сервис принимал задачу, и у неё не оставалось владельца.
Ключи отправок, чей исход ещё не разобран, помнятся (`_sending`): пока ключ в пути, ни поиск по ключу не кончает
запись, ни восстановление не шлёт озвучки заново; ответ «принято» для озвучек, которых уже нет, отдаёт задачу
отмене с её папкой. Когда отправка разобрана, ожидающие записи будятся. Р-53.

## 118. Проверка элементов списка задач не ловилась тестами (ИСПРАВЛЕНО)

Снятие проверки элементов списка задач `jobs()` штатные тесты пропускали: ответ `[{"label": ...}]` без номера
становился достоверным отсутствием искомой задачи. Добавлен тест на такой ответ. Р-53.

## 119. Плееры 1.ruchime.org: решения владельца, протоколы и тупики (справка, перенесена из документов удалённой миссии, 2026-10-31)

Прежние документы (разбор задачи, решения, протоколы, стенды) лежат в истории git: `git show 25647e7:docs/missions/ruchime-players/CHARTER.md`
и `…/ROADMAP.md` (последняя версия).

**Решения владельца (обязательны).**
1. Kodik не используется: 720p недостаточно. Остаются VK, AllVideo, Vibix.
2. Источник серии выбирается по максимальному разрешению; при равном разрешении приоритет VK, затем AllVideo, затем Vibix. Если все
   серии уже в 2160p, нижние плееры не опрашиваются.
3. Разрешение всегда максимально доступное; более высокое разрешение у любого источника — новый файл, композиция перестраивается и докачивает
   лучшее качество. Один файл на эпизод: низкое качество, пришедшее первым, заменяется высоким, файл проигравшего удаляется после того, как
   файл победителя скачан (Р-37).
4. Качество проверяется фактической пробой: автоскан, ручной скан, полный опрос в редакторе правил, добавление ссылки, ручное обновление
   композиции. Открытие композиции web-серии скан не запускает (автообновление выключено), показывает последнее сохранённое состояние.
5. Скан обходит все серии, но исключённые правилами не опрашивает: быстрый список `ALL_EPS`, правила, страницы только неисключённых.
6. Тест правил показывает только факты: полный опрос серий с качеством, даже если это занимает минуты. Плашка разрешения выводится только
   из фактической пробы серии; быстрый разбор релиза качество не подставляет.
7. Браузер — существующий пул модуля `sources`. Ключ расшифровки Vibix не зашит в код: глобальный кэш с TTL 12 часов, при ошибке
   расшифровки немедленный перезапрос.
8. Парсер сам собирает таблицу релиза один раз по запросу, плееры вынесены в общие модули.

**Требования к плеерам.** Плеер — расширяемый список адаптеров, а не ветки в коде; источник выбирается по факту доступности, а не по наличию
кнопки; недоступный источник не становится кандидатом и не уходит в загрузку; ссылка в кандидате разрешается в поток в момент скачивания
(подписанные ссылки протухают); пользователь видит различие «серии на плеере нет» / «видео закрыто» / «серия не загружена»; разбор ссылки
релиза читает только страницу релиза; плееры лежат внутри модуля `sources`; ссылка VK-кандидата остаётся `https://vk.com/video<oid>_<id>`
(от неё зависит идентификатор элемента); поведение внешних плееров утверждается только проверкой на живых данных.

**Плееры.**

| Плеер | Как найти | Проба доступности | Поток | Качество |
|---|---|---|---|---|
| VK | `switchSource('https://vkvideo.ru/video_ext.php?…')` | страница плеера содержит `mp4_<N>`; у части роликов каноническая `vk.com/video…` отказывает («Access restricted»), а плеер с hash открыт | файл по адресу плеера с hash; каноническая ссылка остаётся идентификатором | как выложено |

| Vibix | `switchSource('vibix-embed')` и блок `<ins data-publisher-id… data-id…>` | браузер один раз: подписанный `/api/v1/embed-serials/<id>`, далее HTTP | HLS Kinescope; конверт `{"p","v":1}` | 480/720/1080 |

**Протокол Kodik на Python (без браузера).** (1) `GET https://kodikplayer.com/serial/<id>/<hash>/720p?season=1&episode=<N>&only_translations=…`:
в HTML `var urlParams = '{…}'` (подписи `d_sign`, `pd_sign`, `ref_sign`) и `vInfo.hash` / `vInfo.id` выбранной серии. (2) `POST
https://kodikplayer.com/ftor` (форма: `d`, `d_sign`, `pd`, `pd_sign`, `ref`, `ref_sign`, `bad_user=false`, `cdn_is_working=true`, `type=seria`, `hash`,
`id`, `info={}`): JSON с `links` по качествам, `src` зашифрован. (3) `src`: сдвиг букв на 18 по классу регистра (ROT18), base64, адрес
`//cloud.solodcdn.com/useruploads/<uuid>/<токен>:<ts>/<quality>.mp4:hls:manifest.m3u8`. (4) Манифест — обычный HLS, сегменты — обычный TS (1280×720).
Серию выбирают параметры `?season=&episode=` в ссылке, referer для этого не нужен.

**Протокол Vibix/Kinescope.** Браузер открывает страницу серии, нажимает `data-player="vibix"` и перехватывает запрос
`/api/v1/embed-serials/<id>?…&sig=…`. Ответ — конверт `{"p":"…","v":1}`: строка `p` переворачивается, декодируется из base64 и XOR-ится
с 32-байтовым ключом. Ключ в код не зашит: кэш `torrent_cache/vibix-key.json` (`VIBIX_KEY_STORE`, TTL 12 часов); при истечении или ошибке
расшифровки он восстанавливается из зашифрованного манифеста по известной шапке HLS и проверяется расшифровкой ответа API. Внутри — JSON с
сезонами, сериями и ссылками `[480p]{RuChiMe}https://….m3u8`. Манифест — обычный HLS с абсолютными подписанными ссылками на `.ts`
(подпись живёт около 12 часов), `ffmpeg -c copy` качает без браузера. Стенд — `scripts/vibix_stand` (его `README.md`).

**Тупики (не повторять).** yt-dlp не имеет экстракторов Kodik, Vibix и Kinescope (`--list-extractors`: 1747, ни одного). Vibix без браузера
невозможен: подпись API (`sig`, `nonce`, `meta`) считает обфусцированный SDK. Манифест Kinescope нельзя «просто отдать в ffmpeg»: он приходит
конвертом и перед ffmpeg расшифровывается. Браузер не нужен как загрузчик: он получает ссылку, сегменты качает ffmpeg. Выбор серии Kodik через
referer не работает (с двумя referer сервер отдал одну серию). Разбор всех серий при добавлении сериала на 387 серий занимает минуты и
подвешивает окно: разбор ссылки читает только страницу релиза. Каноническая ссылка VK не единственный путь: для части роликов она отказывает,
хотя плеер с hash содержит рабочий mp4 2160p; загрузка идёт по адресу плеера (`download_url`). Объявленный Vibix-поток не считается рабочим:
плейлист называет потоки, чей манифест CDN отдаёт с 400; кандидат проверяется по манифесту, без потока — явная ошибка, а не yt-dlp по
странице (Р-37).

**Живые серии для проверки.** `https://1.ruchime.org/release/praktikuia-ci-sto-tysiac-let` (387 серий, серия 387 — только Kodik и Vibix);
`https://1.ruchime.org/release/nesravnennyi-boevoi-dux` (VK 2160p, регрессионная); для Vibix с несколькими сезонами —
`https://1.ruchime.org/release/asura-bezumnyi-korol-2`.
