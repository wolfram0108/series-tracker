# Развёртывание (production runbook)

Дата: 2026-11-09. Состояние: актуален.

Пошаговое развёртывание и обновление Series Tracker v2. Прод запускается под
systemd (uvicorn :5000), фронт собирается на месте, БД — SQLite + Alembic.
Развёртывание — **только из git** (ветка `main`), без копирования отдельных
файлов.

---

## 1. Требования к машине

| Компонент | Версия / примечание |
|---|---|
| ОС | Linux (systemd) |
| Python | 3.12 |
| Node.js | 20 (для сборки фронта) |
| ffmpeg | в `PATH` (нарезка, проверка файлов) |
| yt-dlp | ставится в `.venv` из `requirements.txt` (с pycryptodomex); отдельная копия в `PATH` не нужна |
| Firefox | для Playwright — браузерная доставка astar/anilibria_tv |
| Chromium | для Playwright — автоматическое восстановление профиля Alloha |
| qBittorrent | WebUI API доступен (на стенде — Docker-контейнер, `:8080`) |
| NAS / хранилище | смонтировано (пути сохранения сериалов) |

Системные пакеты ставит root; приложение работает от непривилегированного
пользователя (на стенде — `user`).

## 2. Первичное развёртывание

```bash
# 1. Код (ветка main)
git clone -b main https://github.com/wolfram0108/series-tracker.git
cd series-tracker

# 2. Бэкенд: окружение и зависимости
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/playwright install firefox        # для astar/anilibria_tv
.venv/bin/playwright install chromium       # восстановление профиля Alloha
.venv/bin/python -m camoufox fetch          # антибот-челлендж rutracker

# 3. БД: миграции
ST_DB_PATH=app.db .venv/bin/alembic upgrade head

# 4. Секреты запуска
cp .env.example .env
#   заполнить ST_QBIT_URL / ST_QBIT_USER / ST_QBIT_PASS
#   (без ST_QBIT_URL модуль torrents не стартует)

# 5. Фронт: сборка (отдаётся бэкендом с корня /)
cd web && npm ci && npm run build && cd ..
```

Учётки трекеров, VK, TMDB-токен вносятся **через UI** (Настройки → авторизация)
после первого запуска и хранятся в БД — в `.env` их нет.

Alloha получает профиль клиента штатным плеером в Chromium при первом обращении
без профиля либо после явного отказа CDN `session_blocked` / `client_blocked`.
Все загрузки ждут одно общее обновление. Новый профиль проверяется чтением
плейлиста и сегмента через нативный клиент и сохраняется зашифрованным в
`torrent_cache/alloha-profile.enc` с правами 0600. Сохранённый профиль имеет
приоритет над необязательными начальными значениями `ST_ALLOHA_FINGERPRINT`
и `ST_ALLOHA_USER_AGENT`; изменение применяется без рестарта.
Срок действия не предполагается известным. При неудаче есть пауза между
обновлениями, одна загрузка повторяется с новым профилем не более одного раза.
Браузеры устанавливаются от пользователя сервиса; для Alloha не нужен REA
или отдельно установленный системный Chrome.

### systemd-юнит

Готовый юнит — в репозитории: [`deploy/series-tracker.service`](../deploy/series-tracker.service)
(под другого пользователя/путь поправить `User`/`Group`/`WorkingDirectory`/
`ExecStart`).

```bash
sudo cp deploy/series-tracker.service /etc/systemd/system/
```

`start.sh` (в репо) подхватывает `.env` и запускает
`uvicorn run:app --host 0.0.0.0 --port 5000 --timeout-graceful-shutdown 5`
(лимит нужен: SSE-соединения бесконечны, иначе рестарт виснет, пока открыт
браузер).

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now series-tracker
```

### Проверка

```bash
systemctl is-active series-tracker                 # active
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:5000/   # 200
grep '"запущено модулей: 13"' logs/info.log | tail -1             # все модули
```

UI — `http://<host>:5000/`. Старый фронт (аварийный откат) — `/legacy`.

## 3. Обновление (redeploy)

```bash
cd /home/user/series-tracker
git pull origin main
.venv/bin/pip install -r requirements.txt          # если менялись зависимости
.venv/bin/alembic upgrade head                     # если есть новые миграции
cd web && npm ci && npm run build && cd ..          # пересобрать фронт
sudo systemctl restart series-tracker
```

Рабочие данные (`app.db`, `.venv`, `logs/`, `web/dist`) — вне git
(см. `.gitignore`), при `git pull` сохраняются. `web/dist` собирается на месте
и в репозиторий не коммитится — **не забыть `npm run build`** после правок
фронта, иначе UI останется старым.

**Владелец файлов проекта — пользователь сервиса (`user`).** Всё, что пишет в каталог проекта, запускается от него:

| Действие | Команда |
|---|---|
| git | `runuser -u user -- git …`; от root git отказывается («detected dubious ownership») |
| Сборка фронта | `runuser -u user -- bash -c "cd web && npm run build"` |
| Зависимости, миграции | `runuser -u user -- .venv/bin/pip …`, `runuser -u user -- .venv/bin/alembic upgrade head` |
| Проверка | `find . -xdev \( -user root -o ! -group user \) \| wc -l` даёт 0; иначе `find . -xdev \( -user root -o ! -group user \) -exec chown -h user:user {} +` |

Файл, записанный от root, ломает следующую выкатку: `git merge` падает на середине, сборка не может очистить `web/dist`.

## 4. Резервная копия и откат

**Перед миграцией/обновлением** — бэкап БД. Копия снимается на работающем сервисе средствами SQLite, от
пользователя сервиса (от root `sqlite3` создаст файлы `-wal`/`-shm` с владельцем root, и сервис не сможет писать):

```bash
runuser -u user -- sqlite3 app.db ".backup 'backups/app.db.before-<что>-$(date +%Y%m%d)'"
```

Остановка сервиса для копии не нужна: `.backup` даёт согласованный снимок и при открытых соединениях.

**Откат кода** на предыдущий коммит:

```bash
git checkout <предыдущий-коммит-или-тег>
.venv/bin/alembic downgrade <ревизия>              # если откатывали миграцию
cd web && npm ci && npm run build && cd ..
sudo systemctl restart series-tracker
```

**Откат на старую систему (v1):** код заархивирован в теге `legacy/v1-final`
(`git checkout legacy/v1-final`). Это другая архитектура и другой формат
запуска — применять только как крайнюю меру, с отдельной БД/конфигом.

## 5. Эксплуатация

- **Логи:** JSON в `logs/*.log` (error/warning/info/debug, ротация
  RotatingFileHandler). В UI — модалка «Логи» (фильтр групп динамический).
  Каталог логов переопределяется `ST_LOG_DIR`.
- **Дамп синхронизации:** каждая синхронизация сериала (от `scan.run.changed`
  active=true до active=false) пишет файл
  `logs/runs/<номер сериала>/<начало, UTC>-<pid>.jsonl.gz` (модуль `runlog`):
  по строке JSON на каждый конверт шины целиком (`e: bus` — топик, вид,
  correlation id, payload: страницы и их таблицы, раскладка, загрузки со
  ссылками, задачи выравнивания) и на каждую строку журнала любого уровня
  (`e: log`). Планировщик кладёт в шину `planner.sync.trace`: `plan` —
  входы целиком (онлайн-строки, актив, выбор, команды «Удалить», неудачи) и
  план из них на каждом круге (строки источников — в первом круге, дальше они те же); `step`/`done` — шаг графа и его исход;
  `apply` — группа применена или нет и почему. Хранятся последние 50 дампов
  сериала. Чтение (gzip из нескольких частей, по строке JSON):
  `python3 -c 'import gzip,json,sys; [print(l["t"], l["e"], l.get("topic") or l.get("message")) for l in map(json.loads, gzip.open(sys.argv[1],"rt"))]' logs/runs/88/<файл>`.
- **Дамп чтения источника:** чтение страницы вне синхронизации (источник
  добавлен в окне, кнопка «Перечитать») пишет такой же файл —
  `logs/runs/reads/<адрес страницы как имя>/<начало, UTC>-<pid>.jsonl.gz`:
  вся шина и весь журнал от `sources.table.trace` `begin` до `end` этой
  страницы. `end` несёт итог чтения: время, строки каждого плеера по
  состояниям, кадры и каждую причину строки без видео со счётом. Чтение
  внутри синхронизации сериала лежит в дампе этой синхронизации. Хранятся
  последние 50 дампов страницы.
- **Разбор дампа:** `.venv/bin/python tools/analyzers/run_dump.py <файл> [--logs]`
  — для синхронизации и для чтения: фазы чтения с временем и темпом, итог по
  плеерам и причинам, запросы к плеерам (попытки, исходы, секунды) и
  повторная проверка строк без ответа; для синхронизации ещё план, шаги,
  загрузки, выравнивание, применение групп.
- **Перезапуск:** `sudo systemctl restart series-tracker` или `./restart.sh`.
- **Переживание перезагрузки:** юнит `enabled` + `Restart=always`; Docker →
  qBit (`restart=unless-stopped`) → приложение поднимаются сами.
- **Crash-tolerance:** при старте модули добирают незавершённые задачи из БД;
  `torrents` сверяется с qBit (осиротевшие раздачи сбрасываются).
- **Переменные окружения** (`.env`): `ST_CONFORM_URL` (адрес демона выравнивания track-muxer по умолчанию: пока адрес не сохранён в окне «Расширения» — вкладка «Conform» — действует эта переменная; без обоих раздел «Агенты» показывает «адрес не задан»; рабочая папка здесь и на демоне и параметры выравнивания (метод звука, скорость дрейфа, чекпоинты, вырезы оригиналом, края референса из компиляции) — вкладка «Отладка», блок «Сервер выравнивания»; значений по умолчанию в коде нет), `ST_QBIT_URL/USER/PASS` (обязательно для
  торрентов), опц. `ST_DB_PATH` (по умолчанию `app.db`), `ST_LOG_DIR`
  (по умолчанию `logs`), `ST_PROVIDER_URL` / `ST_PROVIDER_TOKEN` (поставщик внешних источников, см. ниже).

### Торрент-источники

Раздача страницы трекера качается qBittorrent'ом в промежуточный каталог: Настройки → «Источники» → «Каталог
промежуточных файлов» (полный путь, одинаковый для приложения и для клиента — у Docker-qBittorrent это `/nas/…`;
смена пути переносит скачанные раздачи). Без каталога «Скачать раздачу» отказывает (`staging_dir_not_set`). Раздачу,
её состояние, автообновление и раскладку файлов по сезонам, сериям, озвучкам и субтитрам показывает вкладка
«Торрент» окна сериала; загрузки раздач — раздел «Агенты», «Торренты в qBittorrent».

### Поставщик внешних источников

Видеоприложения читает отдельный необязательный процесс — поставщик (отдельный проект, не в этом репозитории; запуск, переменные и юнит —
в его собственной документации). Спецификация розетки —
[contracts/provider_socket.md](../contracts/provider_socket.md).

| Что | Как |
|---|---|
| Включить | окно «Расширения» → вкладка «Чинес»: адрес и порт (`http://127.0.0.1:5100`) и токен, когда у поставщика задан `CS_TOKEN`; сохранённое действует сразу, перезапуска нет; там же состояние розетки, приложения поставщика и число его загрузок одновременно. Для развёртывания без окна: `ST_PROVIDER_URL` и `ST_PROVIDER_TOKEN` в `.env`, пока адрес не сохранён в настройках |
| Порядок первого перехода (протокол 2, Р-109) | см. ниже «Переход на протокол 2»; прежний порядок: миграция `0068` (таблица `provider_manifest`) → поставщик запущен с профилями приложений (перенос того, что держал трекер, — его инструменты) → трекер с `ST_PROVIDER_URL`; адреса `app://…` и их таблицы сохраняются: страница, которую перечисляет источник сериала, не забывается, пока поставщик недоступен |
| Состояние | событие `sources.provider.state` (`up`, `down`, `incompatible`) и журнал группы `sources`; причина отказа — `provider_not_connected` (поставщик не подключён), `provider_unavailable` и родственные коды |
| Сериалы, настроенные на приложения | ничего не пересоздаётся: адреса `app://…`, таблицы страниц, ключи и ссылки строк, порядок источников, «Строк на линию», отключённые плееры, файлы и план остаются. Ссылки строк в БД читаются новым правилом манифеста так же, как старым (сверка 30 544 ссылок прод-БД 14.11: расхождений нет). Первое чтение после включения несёт прошлые строки: поставщик не измеряет заново то, что измерено, спрашивает только новые и отсутствовавшие серии. Пока поставщик не запущен, страница, чей сайт не зарегистрирован, отдаёт прежнюю таблицу как неудавшееся чтение (`site_not_found`): синхронизация считает источник устаревшим (`stale`) и идёт по прежним таблицам, а не считает его пропавшим |
| Загрузка | файл серии скачивает поставщик (адрес потока, заголовки, способ, число соединений — его дело) в тот же путь на диске, что назвал трекер; сколько загрузок поставщика идёт сразу — настройка «Загрузок у внешнего поставщика одновременно» (Настройки → Отладка, по умолчанию 2); готовый файл идёт стандартным путём трекера. Поставщик и трекер — на одной машине; память поставщика ограничивает его юнит (`MemoryMax`) |
| Поставщик недоступен или не подключён | пока поставщик не `up` (`ST_PROVIDER_URL` не задан, первого ответа ещё нет, лента оборвана, другой протокол): «Сканировать» у сериала, у которого есть страница мира поставщика (`app://…` или сайт его манифеста), отказывает словами «внешнее приложение не подключено» (HTTP 409) — синхронизация не открывается, ничего не читается и не скачивается; «Перечитать» такой страницы и поиск по приложениям отвечают тем же; автоскан такой сериал пропускает. Прежние таблицы служат. Если поставщик падает посреди синхронизации: чтение кончается видимой причиной и синхронизация идёт с прежней таблицей как с устаревшей, загрузка кончается неудачей, которая источнику не вменяется (`unasked`), прогон закрывается сам и повторится со следующей синхронизацией; трекер подключается сам, когда поставщик вернулся |
| Декларации линий | живут у поставщика; изменение подхватывается `systemctl reload chinese-sources` (`SIGHUP`), трекер узнаёт об изменении манифеста по ленте событий |
| Таблица `share139_folders` | трекером не читается и не пишется; после переноса её строк инструментом поставщика её можно удалить миграцией |

### Переход на протокол 2 (Р-109)

Протокол 1 (источник — карточка двери) снят: трекер принимает только протокол 2, источник — название поставщика (`title://chines/<id>`).
Код протокола 2 выкачен 18.11 (шаг 3 ниже выполнен; сервис работает на нём, источники `app://…` остаются нетронутыми и читаются как «страница мира
поставщика»). Остальное делает владелец, **после завершения разработки поставщика**, с подключёнными прототипами линий и принятыми линиями
([provider_parity.md](../contracts/provider_parity.md), раздел 5): шаги 1–2 и 4–8.

| Шаг | Как |
|---|---|
| 1. Условие | поставщик запущен с адаптерами прототипов (не симуляция), линии признаны, его панель показывает резерв «3 из 3» у нужных линий |
| 2. Бэкап | `runuser -u user -- sqlite3 app.db ".backup 'backups/app.db.before-protocol-2'"` |
| 3. Код | ветка влита в `main`, `cd web && npm run build`, `sudo systemctl restart series-tracker` при простое (`release_tables.state=reading` и `plan_runs` пусты). До усыновления старые источники `app://…` — страницы мира поставщика: синхронизация сериала с ними отказывает словами «внешнее приложение не подключено» либо «поставщик другого протокола» |
| 4. Подключение | окно «Расширения» → «Чинес»: адрес поставщика; состояние `up` |
| 5. План | `.venv/bin/python tools/adopt_titles.py --provider http://127.0.0.1:5100 [--token …]` — на копии базы печатает, что изменится: источники, таблицы, ряды, склеенные источники, **потерянные ряды и файлы, которые на них стоят** (`orphaned`), адреса, которых поставщик не принял (`unadopted`). Файлы на потерянных рядах — отказ переноса: сначала разобраться с поставщиком |
| 6. Перенос | то же с `--apply` (копия в `backups/`, одна транзакция) при простое; затем рестарт сервиса: модули читают базу заново |
| 7. Проверка | `tools/checks/live_api.py sync <номер сериала>` на каждом настроенном сериале: план не меняется (ни пересборок, ни удалений, ни новых загрузок, кроме вышедших серий) |
| 8. Уборка | в коммите выкатки удаляются `tools/adopt_titles.py`, `tests/test_adopt_titles.py` и раздел B спецификации розетки (переходное) |

### Отдельный экземпляр для проверки

Ветка проверяется в своём экземпляре, прод (:5000) и его база не трогаются:

| Что | Как |
|---|---|
| База | пустая, миграциями: `ST_DB_URL=sqlite:///<путь> .venv/bin/alembic upgrade head` (без миграций экземпляр падает на `no such table: settings`) |
| Окружение | `ST_DB_PATH=<путь>`, `ST_AUTH_REQUIRED=false`, `ST_COOKIE_SECURE=false` (иначе кука входа не ставится по HTTP), `ST_SECRET_KEY=<любой>`; `ST_QBIT_URL` не задаётся — модуль torrents не стартует |
| Запуск | `.venv/bin/uvicorn run:app --port <свободный>`; готовность — строка `Application startup complete` в выводе |
| Администратор | новая база встречает окном «Первый запуск»; через API — `POST /api/setup {username, password}` (от 8 символов), он же входит |

### Проверка на живом сервисе через API

После выкатки поведение проверяется на работающем сервисе тем же путём, что у окна. Инструмент —
`tools/checks/live_api.py`:

```bash
.venv/bin/python tools/checks/live_api.py preview "<адрес страницы>" [--now]
.venv/bin/python tools/checks/live_api.py sync <номер сериала>
.venv/bin/python tools/checks/live_api.py source <номер сериала> "<адрес страницы>"
```

| Шаг | Как |
|---|---|
| Вход | `POST /api/login` с `ST_ADMIN_USER` и `ST_ADMIN_PASSWORD` из `.env`. Значения не печатаются. |
| Сессия | Кука сессии помечена `Secure` (сервис работает за HTTPS), поэтому клиент на `http://127.0.0.1:5000` сам её не отправит. Кука из `Set-Cookie` передаётся заголовком `Cookie`. |
| Неудачный вход | Сервис считает неудачи по адресу и на время блокирует его (429). Повторять вход нельзя: сначала разобраться в причине. |
| Таблица страницы | `POST /api/sources/preview {url, refresh: true}` — как окно добавления: таблица в пределах срока актуальности опроса источников (раздел «Отладка», час по умолчанию) отдаётся готовой. `POST /api/sources/read {url}` — чтение сейчас, независимо от возраста таблицы. |
| Источник сериала | `POST /api/series/<id>/sources {url, source_type}` после чтения таблицы адреса — как область источников сериала; `source_type` даёт `POST /api/sources/resolve`. |
| Синхронизация | `POST /api/series/<id>/scan`, затем `GET /api/series/<id>/plan` — файлы плана и неудачи. |
| Конец работы | По потоку событий `GET /api/stream?frames=batch`, без опроса: для чтения — `sources_table_ready` / `sources_table_failed` с каноническим адресом страницы; для синхронизации — `series_updated`, где у сериала появился и пропал статус `scanning`. |
| Запросы к сайтам | Каждый исходящий запрос сервиса записан в `logs/info.log` (строки группы `httpx`); по ним считается, что сервис спрашивал у сайтов и плееров. |

Изолированный прогон сквозного пути: отдельный профиль правил и сериал с библиотекой во временной папке
(`save_path` в `/tmp`). До первой синхронизации все серии, кроме проверяемой, отключаются
(`PUT /api/series/<id>/ignored-episodes {"episodes": {"<сезон>": [номера]}}`). После проверки сериал и профиль
удаляются (`DELETE /api/series/<id>`, `DELETE /api/parser-profiles/<id>`), папка — тоже.
