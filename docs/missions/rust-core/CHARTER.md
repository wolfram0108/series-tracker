# CHARTER — Ядро пересчёта сериала на Rust

> Слой 1. Короткий, меняется редко. Читать ПЕРВЫМ. Прогресс — в ROADMAP.md. Старт 2026-11-19.

## Цель

Полный пересчёт сериала — цепочка «строки раскладки → рычаги серий → план → вид окна и статус» — занимает
сотни миллисекунд на крупном сериале и идёт на одном ядре. При росте хранимых данных в 50 раз это неприемлемо.
По замеру 85% времени уходит не на решение, а на создание, перекладывание и хеширование десятков тысяч мелких
объектов Python. Цель — перенести эту цепочку вместе с её данными в компилируемое ядро на Rust, так чтобы полный
пересчёт крупного сериала занимал миллисекунды и сериалы считались параллельно на всех ядрах. Полный пересчёт
из входов при этом остаётся: инкрементальный пересчёт отвергнут как хрупкий для расширяемости.

## Целевая архитектура

- **Плоскость данных — Rust.** Строки раскладки сериала, действующие рычаги серий, входы плана, план и вид окна —
  неизменяемые структуры Rust. Они создаются из таблиц модуля и дальше не превращаются в объекты Python: модули
  держат одну ручку на данные сериала и передают её по шине. Окну уходит JSON, собранный в Rust.
- **Плоскость управления — Python.** Шина, модули, источники (сеть), правила на первом этапе, исполнение
  (загрузки, выравнивание, ffmpeg, библиотека), шлюз и окна остаются на Python.
- **Счёт без блокировки интерпретатора.** Ядро отпускает GIL на всё время счёта, поэтому пересчёты сериалов
  в потоках пула идут параллельно.
- **Границы модулей сохраняются (Р-7).** Строки раскладки — память модуля раскладки, план — память планировщика;
  обмен — по шине, неизменяемыми ручками вместо словарей.
- **Второй этап — правила.** Разбор названий регулярными выражениями — тот же проход по тысячам строк, он
  переносится после цепочки раскладки и плана.

## Требования

1. Результат ядра совпадает с нынешним Python серия в серию: на всех сериалах копии рабочей базы и на всём
   наборе тестов планировщика, раскладки и симулятора.
2. Контракты шины и данные окон не меняются по смыслу; окно получает то же, что сейчас.
3. Расширяемость не хуже нынешней: новая функция плана — правка в одном месте ядра и её тест. Одна таблица
   на одно знание (как `LAYOUT_PARTS`, `VIEW_INPUTS`), тест-сторож на забытое.
4. Скорость: полный пересчёт крупнейшего сериала (10 тысяч строк, 700 серий) — десятки миллисекунд, не сотни;
   пересчёт всех сериалов на старте использует все ядра. Числа — замером, а не оценкой.
5. Память: строка раскладки и план занимают в разы меньше, чем объекты Python сейчас; размер процесса мерится до
   и после.
6. Сборка — из git на сервере, как фронт: `cargo` при выкатке, никаких собранных бинарников в репозитории.
7. Нет долгоживущих двух реализаций: этап заменяет Python-реализацию своего звена, когда совпадение доказано.
   Python-версия звена удаляется в том же этапе.
8. Тесты проверяют результат, а не язык: Python-тесты остаются тестами поведения; у ядра — свои `cargo test`.

## Критерии успеха

- Ноль расхождений ядра с прежним Python на копии рабочей базы, на каждом переведённом звене.
- Замер зарегистрированным прибором: время пересчёта по сериалам, время пересчёта всех сериалов на старте,
  размер процесса — до и после каждого этапа.
- Сторож цикла событий (`core/loopwatch.py`) не видит остановок от пересчёта.

## Что переиспользуем

- Нынешний Python — эталон поведения на время перевода звена (оракул сверки).
- `tools/checks/plan_real.py` — настоящий сериал из копии базы; сторож цикла; таблицы `LAYOUT_PARTS`,
  `VIEW_INPUTS`; передача раскладки моделью (`composition.layout`).
- Опыт 19.11 (выбор референса на Rust): совпадение на 1052 сериях, счёт ×40–100 быстрее Python.

## Рамки

- Не переносить функции по одной поверх объектов Python: граница съедает выигрыш (ROADMAP, тупики).
- Не вводить инкрементальный пересчёт (решение владельца 19.11).
- Не трогать источники и исполнение: там ожидание сети и диска, а не счёт.
