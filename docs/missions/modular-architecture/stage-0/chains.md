# Цепочки пересчёта: запросы и чистые ступени — основание О-2

Рабочий документ миссии `modular-architecture`. Состояние на 20.11.2026, дерево `e3480f58`. Для каждой цепочки — граф данных: что
спрашивается у соседа, что нужно запросу на входе (вход модуля или промежуточный результат счёта) и куда идёт ответ. Пути
`module.py:NN` — в `modules/composition/` и `modules/planner/`. Номера строк — по ветке прототипа О-1 (после переноса файлов в `calc` и `modules/planner`): в `modules/planner/module.py` они на одну строку больше, чем в `e3480f58`; файлы, которые перенесены, названы новым путём.

Вывод по О-2: запроса, которому нужен результат изнутри чистого цикла по элементу (по строке, серии, цели), в обеих цепочках нет.
Запросы стоят между ступенями. Ближе всего к границе — запрос имён файлов `rules.format_filename` на каждую цель плана (ниже, П-7б):
он зависит от целей первого плана и от него зависит второй, то есть ступени идут «план → запросы → план».

Порядок зависимостей: К-1, К-2 независимы; К-3а зависит от К-1; К-3б — от К-1, К-2, К-3а; К-3в — от К-3б; К-4 — от всех К-3в;
К-5 — от К-4 (**единственный запрос, которому нужен результат счёта по всем источникам**, и он между ступенями К-4 и К-6); К-6 — от К-3,

Что в чистых ступенях мешает чистоте счёта: `_derive` получает `log` и передаёт в `settings.retarget` обратный вызов, который пишет в
журнал (module.py:889-891; `modules/composition/settings.py` → `calc/layout/settings.py`); для `calc` вызов заменяется возвратом списка
замечаний, которые журналит модуль.

Остальные обработчики раскладки, тот же вид:
- `composition.preview` (308-357): `sources.table.get` → `_players_off` → `rules.apply` (К-3в) → `project.voice_names` → `voices.groups.resolve` →
  чистая `_page_preview`. С `lines` — только `rules.apply` и чистая сборка ответа.
- `composition.queues.get` (253-260): `repo.stored`, `voices.settings.get {}` → чистая `_queues_reply`.
- `composition.settings.set`/`set_many`/`reset` → `_edit` (472-489): `catalog.series.get`, `repo.stored` → чистая `_effect_of` → `repo.write`.
- **`_writes_of` → `_markup_copy` → `_level_of` (402-436, 262-264): `voices.settings.get {}` внутри цикла по пунктам команды** — запрос на

  без смены поведения.

Синхронизация вокруг плана: `catalog.series.get` → `repo.run_started`, `_recover`, `_load` → `_inputs` (П-3, П-4) → `prepare()`
(`conform.workspace`) → `executor.sync`: раунд «`plan_of` (П-6, П-7) → шаги графа → новости → `plan_of` снова». Шаги графа — запросы и
команды соседям: `downloads.fetch` (команда), `conform.submit`, `conform.reverse`, `voices.settings.get` на каждый шаг нарезки (436),
`torrents.releases.get` на каждую торрент-строку (476), `conform.job.*`. Они идут между раундами плана, а не внутри `plan()`.

Граница, на которой стоит держать внимание: `plan()` вызывает `namer(slot, video, off)` для каждой цели (`calc/plan/planner.py:456` в
`_goal`), но `namer` — выбор из уже полученных имён (`BusSync._namer`, 342-347), запроса внутри нет. Имена просятся у правил **по одному
запросу на цель** между двумя планами (П-7б); на сериале 46 при пустом кэше имён — 706 последовательных запросов (36–71 мс суммарно),
на сериале 40 — 500. Имена не меняют ни выбор видео, ни дорожки цели (имя — последний аргумент `Goal`, `planner.py:456`), поэтому ключи
запросов П-7б (`slot`, видео, `off`) одинаковы в обоих планах, и структура «план → имена → план» держится. Если правила станут
входом (формат имени сериала приходит один раз, имя считает чистая функция), второй план и запросы П-7б исчезнут; это решение этапа 3,
не условие О-2.

## Что даёт О-2 этапам

- Этап 2 (composition): К-3б, К-4, К-6 — чистые ступени `calc/layout`; между ними запросы К-1…К-3в, К-5 остаются в модуле; запросы К-3а и К-3в
  по источникам независимы (можно слать вместе, но порядок и время запросов не меняют контракта, и в этом этапе не трогаются);
  запрос `voices.settings.get` в `_writes_of` — до цикла.
- Этап 3 (planner): П-4…П-6, П-7в, П-9 — чистые ступени `calc/plan`, `calc/view`; запросы П-1, П-3, П-7б остаются в модуле. Узкое
  место — П-7б (запрос на цель).
