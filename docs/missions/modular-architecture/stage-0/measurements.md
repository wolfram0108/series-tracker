Рабочий документ миссии `modular-architecture`. Дата замеров — 20.11.2026, дерево `main` на `e3480f58`. Сырьё — в `raw/` рядом.
Числа — наблюдения этого дня на этой машине, а не свойство кода: сервис `series-tracker` на ней работает, во время замеров `loadavg`
был 36–45 при 16 ядрах, поэтому время по часам между прогонами расходится на треть. Для сравнения после этапов берётся лучший из
нескольких прогонов и медиана, разница меньше трети не различается.

Условия: Python 3.12.3, pydantic 2.13.4. Копия базы — `app.db` (62 МБ), снятая через `tools/checks/plan_real.py` (`copy_db`,
исходная база открыта только на чтение), миграции доведены до головы этого дерева.

Крупнейший сериал копии — **46** (6 001 строка раскладки, четыре источника-сайта); сериал 40 — второй по строкам

## О-3а. Круг «JSON + повторная проверка» против передачи модели

Метод. Настоящие ответы сериала строятся из копии базы теми же функциями, что у сервиса: `TableGetReply` (хранимая таблица
каждого источника), `RulesApplyReply` (правила профиля к строкам таблицы: `compile_profile`, `process_title`, `result_of`,
`settle_parts`), `CompositionReply` (`layout_of` по хранимой раскладке). На каждом ответе, лучшее из трёх запусков по часам
(`perf_counter`; сборка мусора включена — как у сервиса; второй набор — с остановленной сборкой на время замера, чтобы размер кучи,
оставленной прежними вариантами, не входил в число):

| Вариант | Что мерится |
|---|---|
| круг | `model_dump(mode="json")` у отвечающего + `Модель.model_validate(словарь)` у спрашивающего (так сегодня: `sources/module.py:570`, `composition/module.py:782`) |
| как есть | `Модель.model_validate(объект)` — pydantic отдаёт сам объект; и просто ссылка |
| `frozen` | те же классы с `model_config["frozen"] = True`: построение из тех же данных; проверено, что присваивание поля отказано |
| `frozen` + `tuple` | то же, плюс `list[X]` → `tuple[X, ...]` во всех полях; проверено, что список стал кортежем (словари остались словарями) |

Шина не копирует и не сериализует полезную нагрузку (`core/bus.py`, `core/module.py:_handle_one`, `_consume_replies`): ответ
`composition.layout` уже идёт моделью (`modules/composition/module.py:245-251`).

Наблюдения.
- Круг на сериале 46 для таблиц и правил (то, что `composition._gather` гоняет при каждом пересчёте раскладки) — 147–220 мс;
  полный пересчёт раскладки того же сериала на той же машине — 1,55–2,06 с (О-5б): круг — около десятой части. Раскладку для
  планировщика круг уже не проходит (`composition.layout` — модель); она проходит его только для `composition.get` окнам.
- Передача объекта как есть — 0,02–0,11 мс на ответ (сравнение типа и возврат того же объекта; `assert same is reply` в приборе).
- Построение `frozen`-моделей из тех же данных стоит столько же, сколько обычных: в пределах разброса прогонов (±40 %), устойчивого
  знака нет (раскладка 46: 103,8 против 59,0 при включённой сборке мусора, 47,9 против 35,1 при остановленной). Вариант с кортежами
  в пределах того же разброса. Круг дороже построения в оба раза, так как включает ещё `model_dump`.
- `frozen` в pydantic мелкий: присваивание поля отказано (`assignment_refused` истина на всех 20 ответах каждого набора), а списки и словари внутри
  остаются изменяемыми; глубокую неизменяемость даёт замена `list` на `tuple` в моделях (проверено), словари остаются словарями.
- Пик памяти круга — 10–38 МБ сверх живых данных (второй экземпляр словарей и моделей) на каждый ответ; как есть — 0.

Сырьё: `raw/o3_full.jsonl` (сборка мусора включена), `raw/o3_full_gcoff.jsonl` (остановлена); строка — один ответ и один вариант

## О-3б. Где получатель меняет полученное

Метод. AST всех функций `core/` и `modules/` (2 339 функций): источники — `env.payload`, результат ожидаемого `request`-подобного
вызова (`request`, `_ask`, `ask`, `asked`, `told`, `_step`, `_exported`, `_counts`, `_job`) и `Модель.model_validate(<полученное>)`
(то, что стало бы общим при передаче как есть); след идёт по присваиваниям, подэлементам, `for`, включениям, `.get`, и через вызов
функции, которая меняет свой параметр; копия (`dict()`, `list()`, `.copy()`, `deepcopy`, `model_copy`, `model_dump`, `sorted`)
след обрывает. Поглотители: присваивание полю и элементу, `del`, `setattr`, `.append/.extend/.insert/.pop/.update/.setdefault/.add/...`.
Прибор проверен на образце с восемью известными попаданиями и пятью чистыми случаями.

Найдено 7 строк в 4 местах — все в шлюзе, все над ответами каталога (`catalog.series.list`, `catalog.series.get`, `metadata.map.get`):

| Где | Что меняется |
|---|---|
| `modules/gateway/api_series.py:67` (`build_router`) | `series['tmdb_info'] = mapping` |
| `modules/gateway/api_series.py:80-82` (`list_series`) | `s['last_scan_time']`, `s['downloaded_episodes_count']`, `_attach_tmdb(s, …)` (меняет `s`) |

Строк, где получатель меняет `env.payload` или ответ другого модуля, в `core/` и `modules/` больше нет (проверено и поиском
`\.payload(\[…\])*\s*(\[…\]\s*=|\.(pop|update|setdefault|append|extend|clear|remove)\()` — пусто). Отвечающие отдают свежие словари
(`repository.get_series`, `all_series`), поэтому сегодня правка безопасна; при ответе неизменяемой моделью эти места строят новый словарь.
Побочная находка: `sources/module.py:475-477` кладёт в ответ `on_parse` словарь строки трекера из кэша репозитория (`tracker`) — общий
объект отвечающего, который получатель не меняет.

Сырьё: `raw/o3_mut.json`. Прибор — временный, удалён; метод описан выше.
